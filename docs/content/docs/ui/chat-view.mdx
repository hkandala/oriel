title: "Chat view"
description: "An agent pane drawn as messages with a reply box: launch flags, the transcript followers, sending, waiting, detail levels"
---

An agent pane that Oriel started can show its agent as messages with a reply
box, in place of its terminal. The agent keeps running in its herdr pane. The
chat is a second way to look at the same process, so a switch ends nothing.
It works the same on This Mac and on remote machines, for Claude Code, Codex,
Pi and OpenCode. What is not built yet is in
[Future work](/docs/future-work#smaller-items). Research:
[`chat-view.md`](https://github.com/hkandala/oriel/blob/main/resources/research/ui/chat-view.md)
and
[`agents/`](https://github.com/hkandala/oriel/tree/main/resources/research/agents).

## Which panes have it

- Agents that the [New pane](/docs/ui/new-pane#agent) chooser, Start Agent
  Here or [Relaunch with Chat](#relaunch-with-chat) started with Oriel's
  flags ([Launch flags](#launch-flags)). The second row of their card header
  has the Chat | TUI switch ([Switching views](#switching-views)).
- The app knows such a pane by a marker in the argv of its foreground
  processes, from `pane.process_info`
  ([Program icons](/docs/ui/program-icons#when-the-app-asks-herdr)). This
  also works after the app relaunches, with no state kept in the app. A new
  launch in the same pane is a new chat.
- Every other pane shows only its terminal and no switch: plain terminals,
  agents started by hand or from herdr's TUI, and agents that herdr restores
  after a cold restart (herdr runs them again without the flags). An agent
  among them whose session herdr knows shows Relaunch with Chat in place of
  the switch.
- **The bare-command fallback.** If the shell is in front again at once after
  the launch line (two checks in a row, from 1 s on), the chooser types the
  bare command once more, for every agent. An agent build that refuses
  Oriel's flags then starts with no chat, not with no agent.
- **MetaCode**, the company's OpenCode build, ignores Oriel's plugin and
  sends no state line. After 15 s the chat says "OpenCode has not reported
  its session" and the card flips to its terminal, once. The header shows
  Error only while the card shows the chat. A late line (a slow first plugin
  install) clears it when the card shows the chat again. The app does not
  check the build up
  front: its own `command -v opencode` is not the pane shell's, where an
  alias or a function wins.

### Relaunch with Chat

An agent that runs without Oriel's flags can start again with them, in the
same session. The **Relaunch with Chat** button sits where Chat | TUI sits,
with the help tag "Restart ‹Agent› with chat, in the same session". It
shows when herdr reports the agent and its session (`agent_session`, of the
same agent), the pane's processes carry no marker, and the agent takes that
session value:

| Agent | Session from herdr | Added to the launch line |
|---|---|---|
| Claude Code | a UUID | `--resume <id>`, in place of `--session-id T` |
| Codex | a UUID | `resume <id>`, after the `-c` flags |
| Pi | the session file, an absolute path with no quote and no backslash | `--session '<file>'` |
| OpenCode | its session id | `--session <id>`, before `--port` |

1. While the agent works or needs you, an alert asks first: "Restart
   ‹agent›?", with **Restart** and **Cancel**.
2. The app makes the launch line first (for Pi and OpenCode with its run on
   the machine). If that fails, the notice "‹agent› could not start with
   chat" shows, and the agent keeps running.
3. The card shows the chooser's loader. The app sends the Stop keys if the
   agent works or waits, then ⌃C to clear the prompt, then types the quit
   command (`/exit` for Claude Code and OpenCode, `/quit` for Codex and Pi)
   while the agent still runs.
4. When the shell is in front again and herdr no longer reports the agent,
   within 10 s, the app types the launch line. Otherwise the notice
   "‹agent› did not quit" shows.
5. The loader waits for the agent as for a new one
   ([New pane](/docs/ui/new-pane#agent)). There is no bare-command fallback:
   a plain command would start a new session.
6. The card opens on the chat, because the user asked for it.

- Codex shows its old messages only after the first message, when its hook
  runs.
- With no session from herdr there is no button. The app does not look for
  one in the agent's files.

## Launch flags

`T` is a new lowercase UUID per launch. The chooser types the line into the
pane's shell, so the user's own alias or function for the command still runs
(for example a company `codex` alias). The line reads the same in sh, bash,
zsh and fish (OpenCode: fish 3.4 or later), because its hooks hold no quote
and no backslash.

| Agent | Written first | The launch line | Marker |
|---|---|---|---|
| Claude Code | nothing | `claude --session-id T --settings '<json>'`: inline hooks. A SessionStart hook appends the session's JSON (with `transcript_path`) to `hooks.jsonl`. A PermissionRequest hook for AskUserQuestion only waits for the chat's answer ([Waiting](#waiting)) | the hooks' folder `/.cache/oriel/chat/T` in the `--settings` value |
| Codex | nothing | `codex -c 'hooks.SessionStart=[…]' -c 'hooks.state={…}'`: a SessionStart hook that appends the session's JSON to `hooks.jsonl`, and that hook's trust hash | `/.cache/oriel/chat/T/` inside a `hooks.SessionStart=` argument |
| Pi | `~/.cache/oriel/pi-oriel-<sha8>.ts` | `pi -e ~/.cache/oriel/pi-oriel-<sha8>.ts --oriel ~/.cache/oriel/chat/T/pi.jsonl` | that `--oriel` path, in the argv of `pi` or `pi.real` |
| OpenCode | `~/.cache/oriel/opencode/oriel-tui.js` and its `tui.json`; the launch's password file `chat/T/pw` | `ORIEL_OC_STATE=…/state.jsonl OPENCODE_TUI_CONFIG=…/tui.json OPENCODE_SERVER_PASSWORD=$(cat "…/pw") opencode --port 0 --hostname 127.0.0.1 -- oriel-T` | `-- oriel-T` after `--port` (opencode ignores what follows `--`), and the state line's `pid` is a marked process's |

- Before the line, one run on the pane's machine writes what the line needs
  (Pi and OpenCode), each file whole (a temporary file, then a rename). If
  that run fails, the plain command starts, with no chat.
- The flags write no user config. The user's own settings, hooks, plugins
  and extensions keep working. One exception: a user's own
  `OPENCODE_TUI_CONFIG` is replaced for a chat launch.
- **Codex** runs its hook with `$SHELL -lc` at each session's first prompt,
  not at launch. The trust hash in `hooks.state` is the one Codex keeps for
  that hook, so Codex shows no "Hooks need review" picker
  ([Security](#security)).
- **pi-oriel** is a small pi extension that ships inside the app. Its file
  is named by its content, so two versions of Oriel never fight over one. It
  appends one JSON line to the state file per change: `session {path}`,
  `tree {leaf, at}`, `blocked`, `unblocked`, `working`, `idle` and
  `shutdown`. Only a TUI session reports. While an extension dialog is open,
  it tells herdr's pi integration that pi is blocked, so `agent.prompt`
  refuses. It needs pi 0.80.4 or later (`agent_settled`): an older pi stays
  Working.
- **The OpenCode plugin** checks every 200 ms and appends a line when it
  changes: `{pid, url, session, dialog}`. It reads the server's address from
  the SDK client's private `_client`, so check it on each opencode release.

## Where messages come from

| Agent | History | Phase |
|---|---|---|
| Claude Code | the `transcript_path` of the last SessionStart line | `status` in its session record `~/.claude/sessions/<pid>.json`: `idle` and `shell` are ready, `busy` works, `waiting` waits. Without a record, herdr's status |
| Codex | the `transcript_path` of the last SessionStart line that has one (its rollout) | herdr's status, and [the screen check](#codexs-screen-check) |
| Pi | the `path` of the last `session` line; `tree` lines move the branch ([Pi's tree](#pis-tree)) | the state file alone: `working`, `idle`, `blocked` until `unblocked`; starting before the first `session` line and after `shutdown` |
| OpenCode | `GET /session/<id>/message` for the session in the last state line, then `GET /event` (opencode writes no transcript file) | a dialog or a pending request waits; a busy `session.status` works; else herdr's status |

- **The followers** run on the pane's machine, through `run`: a `Process` on
  This Mac, the relay on a remote machine
  ([Running commands](/docs/talking-to-herdr#running-commands)).
  - `Exec.follow` follows a file as `tail -F` does. It waits for the file,
    tells its inode, where it reads from and where the file's whole lines
    end. It sends those whole lines with `head`, after a seek (`dd … count=0`),
    then runs `tail -c +N -F` from their end, into awk when the agent has
    lines to skip. macOS's `tail`
    copies only about 17 MB a second, so it never reads the backlog. A new
    file is read whole, from its start: one Claude Code turn can pass
    256 KiB.
  - **The line filter.** awk drops the lines that the agent's parser skips
    (an awk pattern next to each parser) and prints `oriel-skip <bytes>` in
    their place, so the mark still counts the file's bytes. On a remote
    machine only the lines the chat reads cross the relay. Claude Code: the
    records that write another `type` first (`api-request-*`, …) and
    attachments other than queued prompts. Codex: every top-level type but
    `event_msg` and `turn_context`. Pi's file passes whole (its tree needs
    every entry), with no awk: macOS's awk passes about 30 MB a second. A
    796 KB Claude Code session sends 208 KB.
  - awk reads a FIFO that only `head`, then `tail` write to. The wrapper's
    kill ends `tail`, or ends `head` through a trap, so a dropped follow
    sends no more of its backlog, and awk ends too. mawk (Debian's and Ubuntu's awk) runs with
    `-W interactive`, or it holds lines until 8 KiB come. The filter runs on
    This Mac too.
  - **Shown once loaded.** The chat reads the file up to the end of its
    whole lines at the open into a backlog, off screen, then shows it at
    once. Lines after that show as they come. A read that is cut short keeps
    what it read. The read yields every 200 lines: a 106 MB pi session loads
    in under a second. There is no loader: a local read of a usual session
    takes milliseconds.
  - The chat keeps a mark (inode and offset) per file in memory, so a card
    shown again goes on from there. Another inode, or a shorter file, starts
    the file again.
  - `Exec.watch` prints a rewritten file (Claude Code's session record) whole
    on each change, checked every 0.3 s.
  - OpenCode's are `curl` runs on the pane's machine against
    `http://127.0.0.1:<port>`. The history loads after the event stream says
    `server.connected`, so no event falls between the two. Each event builds
    the history again whole (Simpler choice: a long session is megabytes).
- A new session line (`/clear`, `/new`, a fork, a resume) starts the history
  again.
- The adapter follows only while a card shows the chat. Off screen, the
  header's state is herdr's. A dropped stream is followed again after 2 s,
  from the marks.
- A message shows when it is on disk, 0.1–2 s after the TUI draws it. There
  is no text word by word. While the agent works, the last row is the
  working dots and "Working" with the turn's time ("Working 29s"), the
  chat's one loader.
- **Parsers.** One small, lenient parser per agent, in HerdrKit
  (`ClaudeTranscript`, `CodexRollout`, `PiTranscript`, `OpenCodeSession`),
  fills one `ChatHistory`: user text, replies, thinking, tool calls paired
  with their results (an edit with its diff), todo lists, notes
  ("Interrupted", an API error, a compaction), turn ends, and the model and
  thinking effort of the last reply.
  Anything else is skipped. Five lines in a row that do not parse are a
  problem ([Waiting](#waiting)). A tool the parser does not know shows its
  own name (an MCP tool's last part) and its first text argument by key.
- Codex's parser reads only whole items (`item_completed`), `task_complete`,
  `turn_aborted`, `error` and `turn_context`. A plan reads as a reply.
- **Markdown:** parsed by Apple's `swift-markdown` (cmark-gfm) and drawn
  with SwiftUI, block by block ([What it looks like](#what-it-looks-like)).
- **Model and effort.** The model as the agent writes it. The effort is
  Claude Code's `effort` field, Codex's `turn_context.effort`, pi's
  `thinkingLevel` and OpenCode's `variant`, and none when the files have
  none.

## The adapter interface

One protocol, `ChatAdapter` in `Oriel/Chat/ChatAdapter.swift`, fits every
agent. `ChatAdapters.all` lists the four.

```swift
protocol ChatAdapter: Sendable {
    static var command: String { get }                 // the chooser's command, herdr's agent name
    static func flags(_ token: String) -> String       // added to the command
    static func prepare(_ token: String, on exec: any Exec) async -> String?  // the whole line; nil: plain
    init?(_ foreground: [Program.Foreground])          // the marker in pane.process_info's argv
    var token: String { get }
    var stopKeys: [String] { get }
    @MainActor func follow(_ chat: Chat, on exec: any Exec) async   // history, phase, question, problem
    func answer(_ question: ChatQuestion, _ answers: [String: String], on exec: any Exec) async  // optional
}
```

The core (`Chat`, the views) does the rest: sending, Stop, text that starts
with `/`, the drawer and the layout. `Chat.follow(history:on:read:)` follows a
history file for any adapter.

## Ready, working, waiting

The phase is the adapter's own record when it has one, else herdr's status:
needs you waits, working works, idle and finished are ready, and a pane herdr
does not know yet is starting.

### Codex's screen check

herdr reports a Codex picker or dialog as idle. So while herdr says idle or
working, the adapter reads the pane's last 8 lines every 0.5 s
(`pane.read {source:"recent"}`).

- Codex is ready when its input box (`› …`, not a numbered picker row
  `› 1. …`) sits directly above its status row (`… · …`), among the last 4
  rows with text.
- Two misses in a row make the chat wait, so the live terminal shows and
  nothing is sent into the picker. When a card shows the chat again, the
  first read alone decides.
- It reads `recent`, not the viewport, so a scrolled pane is not a picker.

### Pi's tree

pi writes nothing to its transcript on `/tree`. pi-oriel writes a `tree`
line with the new leaf and `at`, the transcript's size at the move.

- The leaf moves when the transcript is read up to `at`. A move that the
  transcript was read past is dropped (a card shown again after turns in the
  terminal).
- The parser keeps each entry's parent and its steps, so another branch is
  built again without a new read of the file.
- `branch_summary` and compaction are notes. `custom_message` is skipped.

## Sending and stopping

- **Send:** Return or the Send button gives `agent.prompt {target, text}`,
  only while the agent is ready or working. ⇧Return and ⌥Return add a line.
  herdr pastes the text with bracketed paste and presses Enter. herdr refuses
  unless a foreground process has the agent's name.
- While the agent works, Send stays on. Claude Code and OpenCode queue the
  text. Codex and Pi steer the turn with it: the history gets it after the
  running tool.
- **Sent** means the user entry showed up in the history, matched by its
  text. Until then the bubble is dimmed. After 5 s, and once the agent no
  longer works or waits, it shows "Not sent" with **Show TUI**, and the
  draft comes back when the reply box is empty. A late entry still clears it.
- Text that starts with `/` is not sent. The card flips to its terminal, and
  the text is typed there with `pane.send_input`, with no Return.
- **Stop** takes Send's place while the agent works and the reply box is
  empty. It sends `pane.send_keys` Esc (OpenCode: Esc twice, because the
  first only arms the interrupt). Never ⌃C.
- **Esc** anywhere in the chat stops the agent as Stop does, while it works.
  While it is idle, Esc does nothing. The chat must have the keyboard: the
  reply box almost always has it, but not after a double-click selected
  text. While the drawer shows, its terminal takes Esc.
- The draft is kept in memory per pane, shared by every card of the pane.

## Waiting

When the agent waits on something the chat can answer, a question card shows
above the reply box. Its buttons are the options. An answered card stays,
disabled, until the agent goes on.

- **Claude Code's questions** (AskUserQuestion, single choice). The hook
  writes its pid to `ask`, appends the question to `hooks.jsonl`, and waits
  for `answer`, at most 30 minutes, while `ask` still holds its pid and
  Claude Code lives. The card writes the decision (allow, the questions
  echoed, the answers by question text) to `answer`, whole, only while `ask`
  is there. If the user answers in the TUI first, the session record leaves
  `waiting`, the app removes `ask`, and the hook exits.
- **OpenCode's permissions and questions**, from the event stream (and
  `GET /permission` and `GET /question` on connect), oldest first. A
  permission reads "Bash: touch x" with **Allow once**, **Allow always** and
  **Reject** (the TUI's words), sent to `POST /permission/<id>/reply`. A
  question goes to `POST /question/<id>/reply`. A request answered in the TUI
  sends a `replied` event, and the card goes. Every pending request on the
  TUI's own server counts, subagents' too.
- A question with several answers (Claude Code's `multiSelect`, OpenCode's
  `multiple`) or with no options goes to the live terminal.

**The live terminal.** When the agent waits on anything else, the bottom of
the card (45 % of its height, at least 160 pt) becomes the live terminal, in
place of the reply box. Its header says "‹Agent› is asking in the terminal",
with **Open TUI**, which flips the whole card. It gets the keyboard.
When the agent works or is idle again, it goes, and the reply box takes the
keyboard back. This covers tool approvals, Codex's questions, Pi's extension
dialogs and every picker.

**The chat cannot read the session.** A red card says so, with the reason
and **Show TUI**, and the header's capsule says Error:
- "‹Agent› has not started a session": Claude Code or Pi after 10 s with no
  session, or Codex when a message is not sent and its hook never ran.
- "OpenCode has not reported its session" ([MetaCode](#which-panes-have-it)),
  "OpenCode's server did not answer" or "did not give the session".
- "The transcript is not in a format the chat knows".

## Detail levels

One setting for the app (`chatLevel`, Replies by default): **Replies**,
**Activity** and **Everything**, in the `Show: Replies ⌄` pull-down left of
Chat | TUI. It shows only while the chat does. A saved `steps` or `all`
reads as Replies.

- **Replies:** the user's messages, and for each turn its quiet line on
  top, its last reply, its notes and, once the turn ends, "Worked 1m 48s"
  under them in 12 pt secondary text. The quiet line counts every tool call
  of the turn and does not open: "Read 9 files, ran 4 commands, 1 failed".
  It has no state and no time: while the turn runs, the loader under it
  says "Working" and the time. A turn with no tool calls has neither line.
- **Activity:** the same rows, at the same place and height. Only here the
  turn's line has a chevron and opens to every step of the turn: its tool
  calls and its thinking.
- **Everything:** no turn line and no "Worked". Every reply, todo list and note, each run of
  tool calls between two replies as one quiet line, open, and thinking alone
  as a "Thought" row.
- A line or run clicked open or closed stays so at every level.
- No line or run has working dots: the loader is the chat's last row. While
  a turn streams, a closed line changes only its counts.

**Tool calls.** A run is one quiet line with no card: its summary, a chevron
and the time.
- The summary uses pi-content-layout's words
  ([`tools.ts`](https://github.com/hkandala/pi-hkandala/blob/master/extensions/pi-content-layout/tools.ts)):
  a verb and a noun per tool for every agent's tool names, calls counted
  (not distinct files), on one line: the three largest counts first (a tie
  in the order the tools first ran), the others as "+N more", then the
  failures: "Ran 89 commands, talked to 69 agents, stopped 26 agents, +4
  more, 4 failed". A tool it does not know reads "ran ‹tool› N times". The
  tool calls of a codemode script count as their own.
- As in its groups, thinking between tool calls is a step of the run (a
  "Thought" row inside it).
- Open, a run has one row per step: a symbol for its kind, the tool, its
  target, its result (failed in red, a spinner while it runs), its time and
  a chevron (`bash npm test exit 1   4.2s`). The symbols are squares and
  rectangles of one size: `doc.text` (read), `square.and.pencil` (edit),
  `terminal` (command), `doc.text.magnifyingglass` (search),
  `curlybraces.square` (other) and `text.bubble` (thinking).
- A call opens on its own to its **Input** (an edit's diff instead, the
  first 40 lines) and its **Output**: 11 pt monospaced, selectable, at most
  180 pt tall, then it scrolls. It is a vertical scroll view around a
  sideways one, because inside the strip a scroll view of both axes gets no
  vertical wheel. The parsers keep each call's input and output whole, up to
  20 000 characters.
- A todo list sits on a faint fill.

## What it looks like

- As in Messages: the user's messages are bubbles in the accent color on the
  right (14 pt, radius 18). They are Markdown, drawn as the replies are, in
  the bubble's text color (links too), with their own line breaks kept. Replies are plain, selectable text on
  the left.
- Rows sit 10 pt apart, and a user's bubble has 8 pt more above and under
  it, so each turn reads as one block.
- **An empty chat** shows the agent's program glyph (the one in the tab), 64
  pt and gray, in the middle of the messages, until the first message.
- The messages, the question card and the reply box sit in a 760 pt column,
  centered on any card, 32 pt in from its sides. The messages scroll, newest
  at the bottom, and fade in under the header. In a floating window they
  start 28 pt under the title row, not 16 pt, because the card has no header
  there.
- **Scrolling.** The messages are a lazy stack: only the rows near the view
  are built. At the bottom, the chat stays at the bottom as messages come and
  as the card resizes. Scrolled up, the message at the top stays at the top
  instead.
- **Resizing.** A narrow card (under 824 pt, where the column narrows too)
  lays its messages out at its new width once the width stops changing for
  150 ms, as a terminal does: a split's motion or a drag wraps the text once,
  not at every frame. Meanwhile the card clips the messages, or its fill
  shows beside them.
- **Scroll to Bottom.** While the bottom of the messages is more than 40 pt
  out of view, a round glass button with a down arrow (30 pt) sits 10 pt
  above the reply box, in the middle. A click jumps to the newest message.
- **Over the messages.** The question card and the reply box sit over the
  bottom of the messages, which scroll under the glass. The last message
  scrolls clear of the box as it grows. This is the one place where
  something sits over pane content, because the user asked for it. The live
  terminal keeps its own row under the messages. Simpler choice: a wheel
  over the reply box does not scroll the messages under it.
- **Markdown.** `swift-markdown` (cmark-gfm) parses it. 14 pt text with
  4 pt line spacing. Headings are 22, 18 and 16 pt (bold for the first two
  levels), with 22 or 16 pt above them and 8 pt under them. 12 pt between
  other blocks, 6 pt between list items.
  - List items hang behind their number, bullet (•, ◦, ▪ by depth) or task
    box (`square`, `checkmark.square.fill`), and a list item's later blocks
    line up under its text. Lists and quotes nest.
  - Inline code is at 0.9 of its text's size on a faint fill. Code blocks
    are 12.5 pt monospaced and scroll sideways. Quotes are secondary, behind
    a 3 pt bar. A rule is a divider. Strikethrough is drawn. HTML shows as
    written.
  - A table sits in a faint frame (radius 8): the head row on a fill, a line
    between rows, each column aligned as written.
  - Links open only for `http`, `https` and `mailto`. Bare `http://`,
    `https://` and `www.` addresses are links too (`NSDataDetector`:
    swift-markdown has no autolinks), names such as `Oriel.app` are not.
  - An image shows as its description, linked to its address. The chat never
    fetches it: a reply could send what the agent read to any server.
  - Footnotes read as written (`[^1]`): swift-markdown has none.
- **The reply box.** A glass box (radius 18) with "Ask Anything", 14 pt. Its
  text is 14 pt in from the box's sides, and the box is 18 pt in from the
  column, so the text lines up with the messages' 32 pt edges. It grows from
  1 to 10 lines, then scrolls. Under
  the text, on the left: the model and the effort in 11 pt secondary
  ("Opus 5.5 · high"). Claude's model ids read as the family and version.
  Other models show as the agent writes them. On the right: a 22 pt round
  Send, in the accent while it can send, or Stop.
- **A click anywhere** on the chat, on text too, gives the reply box the
  keyboard (the drawer's terminal while the drawer shows). A button or a link
  acts as well. A double or triple click, a ⇧-click or a ⌃-click leaves the
  keyboard where it is, so selected text can be copied.
- **The header.** Row 1: the pane's name ([Session titles](#session-titles)),
  the state capsule (Working, Needs you, Done or Error, in the status colors,
  and none while idle) and the card buttons. Row 2: the program glyph, the
  agent's name and the folder, then `Show: Replies ⌄` and Chat | TUI in
  the app's own pill segments
  ([Pane card](/docs/ui/window#pane-card)).
- The reply box takes the keyboard when the chat appears and when the drawer
  goes. The keyboard moved to a chat card goes to its reply box.

## Switching views

- Chat | TUI is in the card header, not a swipe: sideways swipes belong to
  the strip. TUI is the agent's own terminal interface.
- A card of a marked pane opens on its TUI; the user switches to Chat. After
  [Relaunch with Chat](#relaunch-with-chat) it opens on the chat. The choice
  is kept in memory per pane, for every window of the session. The card keeps
  the keyboard across a switch: the reply box or the terminal.
- A floated chat pane shows its chat in its floating window, with `Show` and
  Chat | TUI in the window's title row
  ([Floating pane](/docs/ui/window#floating-pane)).
- The switch changes only what the card draws: the agent, its turn and its
  pane go on. The terminal stream stays open while the chat shows.

## Session titles

An agent pane's name is the user's herdr label, else its session's title,
else "Untitled". It shows in the card's row 1, the floating window's
title row, the tab ("Claude Code" then the name in secondary text) and the
Agents view's rows. It works for every agent pane, with or without a chat.

herdr's `agent_session` on each pane names the agent's session: an id for
Claude Code, Codex and OpenCode, the file for Pi. The app uses it only when
its agent is the pane's agent. One `sh` run on the pane's machine reads the
title, and again when the session, the terminal title or the status changes
(agents name a session during a turn, and pi's `/name` retitles its
terminal). The runs share the gate of the program asks, so a session's first
snapshot does not start every run at once.

| Agent | Where the title is |
|---|---|
| Claude Code | the last `custom-title` line (from `/rename`), else the last `ai-title` line, in the session's transcript `~/.claude/projects/*/<id>.jsonl` |
| Codex | `thread_name` on the session's last line in `~/.codex/session_index.jsonl` |
| Pi | the last `session_info` line (from `/name`) in the session file. pi names no session by itself |
| OpenCode | `session.title` in its database, read with `sqlite3 -readonly`. Its placeholder "New session - …" counts as none |

- An id goes into the script only when it holds letters, digits, `-` and `_`
  only. A file must be an absolute path.
- A title loses its control characters and is cut at 200 characters.

## Side files

All of them are under the home folder of the pane's machine, so they are the
user's own on a shared machine.

| File | Written by |
|---|---|
| `~/.cache/oriel/chat/T/` (0700) | the launch: `hooks.jsonl`, `ask`, `answer` (Claude Code), `hooks.jsonl` (Codex), `pi.jsonl` (Pi), `state.jsonl` and `pw` (OpenCode) |
| `~/.cache/oriel/pi-oriel-<sha8>.ts` | the app, before a Pi launch |
| `~/.cache/oriel/opencode/oriel-tui.js`, `tui.json` | the app, rewritten before each OpenCode launch |

**The 30-day sweep.** Each launch deletes side files untouched for 30 days,
then empty folders more than a minute old, so a folder that a launch just
made stays. Claude Code's and Codex's hooks do it at each session start, and
the run before a Pi or OpenCode launch does it too. It goes by the files' times,
because an append does not change a folder's time. Simpler choice: a pane
open 30 days with no writes can lose its side files (OpenCode's server then
does not answer).

## Security

- **OpenCode's password.** The server listens on 127.0.0.1 only, with a port
  the system picks. Each launch gets 16 random bytes, in hex, in `chat/T/pw`
  (0600, in a 0700 folder). The typed line moves it from the file into
  opencode's environment, so it never shows in argv or the scrollback. `curl`
  reads it from a here-document. opencode's tools inherit it (the same user).
  The state line's url must be exactly `http://127.0.0.1:<port>`, and its
  `pid` a marked process's.
- **Codex's hook trust.** The app passes the trust hash of its own hook only:
  sha256 of the hook's JSON with Codex's defaults, under the `-c` layer's
  key. Codex runs that hook without a question, and every other hook still
  needs review. No bypass flag.
- **Claude Code's hooks** come in the inline `--settings`, so nothing is
  written to the user's settings. The user's and the company's hooks run
  too.
- Simpler choice: a home folder with a space gets no chat (`$HOME` is not
  quoted in the hooks). OpenCode's `tui.json` breaks on a home folder with a
  `"`.

## Tests

The UI tests start a stand-in per agent, `scripts/<command>-stand-in.py`, by
its place in the chooser, on CI, on This Mac and on the remote test host. A
stand-in runs again under the agent's name (herdr's `agent.prompt` needs a
foreground process of that name), acts on the flags as the agent does, writes
the agent's format, and reacts to input: a dialog, a question, a slow turn, a
dropped prompt, an echo.

## Check by hand

The stand-ins cannot cover the real agents. Start each one from the chooser,
on This Mac and on a remote machine, in light mode and in Classic.

- **Claude Code:** a reply. A question answered in the chat, and one
  answered in the TUI. A tool approval with permission prompts on (the
  drawer). `/clear` in the terminal: the chat starts the new session.
