Not built. This page is the design of the chat view: an agent or terminal
pane drawn as messages with a reply box, instead of its terminal. The agent
keeps running in its herdr pane; the chat is a second way to look at the same
process, so switching ends nothing, and it works the same on remote machines.

## Where messages come from

1. Find the transcript from the pane's `agent_session`: a path when herdr
   gives one (pi), else an id (Claude Code, Codex).
2. Find the file on the machine: `ls`, or `lsof` for Codex.
3. Tail it with `tail -c +N -F`: new lines arrive as the agent writes them.
4. Parse each line into user text, assistant text, thinking and tool calls.
5. Draw the messages: Markdown, with tool calls collapsed.

herdr keeps no chat history, but it knows where each agent writes its own
transcript: `agent_session` on the pane.

| Agent | `agent_session` | Transcript file on the machine |
|---|---|---|
| pi | `kind:"path"` | that path |
| Claude Code | `kind:"id"` | `~/.claude/projects/*/<id>.jsonl` |
| Codex | `kind:"id"` (a hint only) | the `rollout-*.jsonl` file the pane's codex process holds open |

### Codex and missing integrations

- Codex starts a shared app-server daemon by default and its TUI attaches to
  it. The daemon then runs the hooks and writes the rollouts, so herdr's id can
  point at another pane's thread. The app checks the pane's foreground
  processes for an open rollout file (`lsof -p <pid> -Fn`, or `/proc/<pid>/fd`
  on Linux). A Codex started with `--no-daemon` (herdr's advice for its
  integration) holds its rollout open; a Codex on the daemon does not, and its
  pane uses the screen-text chat.
- Claude Code and Codex report `agent_session` only when herdr's
  integration is installed. If it is missing, the pane uses the screen-text
  chat. The app shows no text that tells the user to run a herdr command
  (an installer for agent integrations is left out on purpose,
  [Future work](/docs/future-work#left-out-on-purpose)).

### Read and parse

- **Read:** the app finds the file once. Then it runs one long-lived
  `tail -c +<offset> -F <file>` on the machine (the chat tail), wrapped so a
  closed channel ends it. New lines arrive as the agent writes them. A chat
  tail has no timeout, like the other long-lived streams; the
  [health check](/docs/machines#health-check) finds a dead one.
- On open it reads the last 256 KiB and drops the first partial line. Simpler
  choice: no older history in v1. Revisit when users ask for history older
  than the last 256 KiB.
- **Parse:** a small, lenient parser per agent turns lines into messages:
  user text, assistant text (Markdown), thinking (collapsed), tool calls and
  results (one collapsed row each), images. Unknown lines are skipped.
- **Markdown:** `AttributedString(markdown:)` with the `.full` syntax option,
  split into blocks. Code blocks are monospaced and scroll sideways.
- **Session changes** (`/new`, `/resume`) do not always send an event, so
  while a chat view is open the app re-checks `agent_session` on each
  snapshot and after each send, and restarts the tail when it changes.
- **More parsers** come later, one per agent that writes a transcript.
- **Working row:** agents write a message to the transcript when it is done,
  not word by word. While `agent_status` is `working`, the last row says
  "Working".
- **Known limits:** pi transcripts are trees and are read in file order.
  A custom `CLAUDE_CONFIG_DIR` is not followed in v1, until herdr reports
  Claude Code's path too
  ([Waiting on herdr](/docs/future-work#waiting-on-herdr)). Codex needs no
  folder: `lsof` gives the full path.

## Screen-text chat

- Agents without a parser, agents without `agent_session`, and plain
  terminals get a "screen text" view. So every agent pane and every terminal
  pane can switch to chat. Web and plugin panes have no chat view.
- It shows `pane.read {source:"visible", format:"text"}` as monospaced text,
  re-read every 1 s while shown and once 300 ms after each send.
- The reply box sends `agent.prompt` to agents and `pane.send_input {text,
  keys:["enter"]}` to terminals.

## Sending and answering

- **Send:** `agent.prompt {target: pane_id, text}`. herdr pastes with
  bracketed paste and presses Enter in one step.
  - `agent_blocked`: herdr refuses while a dialog is open, so a message can
    never approve a prompt by accident. The draft is kept.
  - `agent_not_ready`: "Agent is starting". The draft is kept.
  - While the agent is working, Send stays on; the text joins the agent's own
    input queue.
- A pasted image becomes a path in the draft
  ([Image paste](/docs/future-work/plugins/agent#image-paste)).
- Sends to one pane go one at a time, in order. Drafts are kept in memory per
  pane and shared with the pill card.
- **Blocked panel:** the bottom of the screen (`pane.read {source:"detection",
  format:"text"}`) and key buttons that send `agent.send_keys` with `"up"`,
  `"down"`, `"enter"`, `"esc"`, `"1"`, `"2"`, `"3"`. **Open terminal** flips
  the card to the terminal view. There is no per-agent prompt parsing.
- **Key guard:** while the panel is shown, its text is re-read on every
  snapshot change for that pane. On a click the app reads it once more and
  sends the key only if the agent is still blocked **and** the text is
  unchanged. Otherwise it shows "Prompt changed, not sent". The prompt may
  have been answered on another device. A spinner tick can cause a false
  "changed", which is the safe failure.

## Switching views

- Agent and terminal cards have a chat|term switch. It is a segmented control in the card header, not a
  swipe, because sideways swipes belong to the strip.
- The choice is kept in memory per pane. The Mac and the phone can show the
  same pane differently.
- The switch changes only what the card draws: the agent, its turn and its
  pane go on. While the chat view is shown, that pane's terminal stream is
  closed; switching back opens it again.

## What it looks like

- The card keeps its header, with the chat|term switch. Under it the
  messages scroll, newest at the bottom, and the reply box sits at the
  bottom of the card.
- If the agent needs you, the blocked panel shows the bottom of its screen
  and the key buttons, above the reply box.
- The same view, smaller, is the [floating pills](/docs/future-work/pills)'
  pill card.

## Choices

- **The agent's transcript, tailed on the machine, plus `agent.prompt`**;
  parsers for pi, Claude Code and Codex; a screen-text chat for every other
  agent or terminal pane. Any agent or terminal pane can switch, and nothing
  ends. Rejected: per-agent prompt parsers;
  parsing the screen into fake messages.
- **The key guard.** The prompt may have changed on another device. Rejected:
  sending without a check.
- **No structured mode.** Rejected: restarting the agent in a structured mode
  (Claude Code's stream-json, `codex app-server`, `pi --mode rpc`) or through
  ACP. It ends the agent to switch, needs a fork to come back (two processes
  must not write one session), takes a large adapter per agent, and on a
  remote machine the process would die with the SSH link, where a herdr pane
  lives on.
- **Later, Codex only:** codex's app-server sends a thread's events to every
  client that resumed it, so a chat could join the running thread of a Codex
  on the daemon, with live text. Revisit when users ask for it; it needs a
  reliable way from a pane to its thread and a line adapter on the relay (the
  socket speaks WebSocket).
