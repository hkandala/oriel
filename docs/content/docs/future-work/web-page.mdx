Not built. This page is the design ([Pane kinds and plugins](/docs/future-work/plugins)).
Research and measurements:
[`browser.md`](https://github.com/hkandala/oriel/blob/main/resources/research/plugins/browser.md).

herdr cannot draw a web page. So a herdr pane holds the place in the layout,
and the app draws a browser in its rectangle. The browser is the first pane
kind built on the [plugin foundation](/docs/future-work/plugins#the-first-slice).

## The engine

On the Mac the page is Chromium, through CEF (Chromium Embedded Framework),
so Chrome DevTools come with it. iPhone and iPad use WebKit, as Apple
requires.

- Each card holds one CEF browser as a child `NSView` (CEF calls this Alloy
  style; on macOS a child view is always Alloy style). Chromium handles
  typing, IME, trackpad scrolling and accessibility itself. SwiftUI views
  drawn over the page (sheets, the find bar) show above it.
- A small Objective-C++ shim wraps CEF's C++ API: one `NSView` class (load,
  back, forward, reload, stop, find, DevTools, and callbacks for the address,
  title, loading and errors), the `NSApplication` subclass CEF needs, and the
  message pump. Swift cannot subclass CEF's C++ handler classes.
- **The app object:** SwiftUI ignores `NSPrincipalClass`, so `App.init()`
  creates CEF's `NSApplication` subclass before SwiftUI makes its own, and
  SwiftUI adopts it.
- **The run loop:** CEF's `external_message_pump`. CEF asks for work through
  `OnScheduleMessagePumpWork`, and the app runs `CefDoMessageLoopWork` from
  timers on the main run loop in common modes, so pages keep running during
  drags and menus.
- **Processes:** Chromium's browser process is the app itself. The GPU, the
  network, storage and one renderer per site run as helper apps. A hung page
  freezes only its renderer.
- **The bundle:** the framework (about 333 MB, arm64) and five helper apps in
  `Contents/Frameworks`, signed inside out with the hardened runtime and
  `com.apple.security.cs.allow-jit` (and `disable-library-validation` while
  the app is signed ad hoc). There is no Mac App Store path.
- **Updates:** CEF ships a branch about every 4 weeks, and security builds
  trail Chrome by 2 or 3 days. The app pins one exact build, as it pins
  libghostty-spm: a script downloads it and checks its SHA-256.
- **Its own folders and keychain item:** CEF's `root_cache_path` is under
  `~/Library/Application Support/Oriel/Browser/`, and cookies are encrypted
  with a keychain item of Oriel's own. Stock CEF uses the shared "Chromium
  Safe Storage" item, which asks for the login password and holds every
  request until the user answers.
- Chromium's background requests (component updates, autofill queries) are
  off, so nothing loads that the user did not ask for.

## The marker is the pane label

The label is the marker: `oriel:browser#<iid> <url>`, for example
`oriel:browser#m4p8sa http://localhost:3000/dashboard`
([Labels and instance ids](/docs/future-work/plugins/labels)). The label is
the only pane field that has no length limit and survives moves and herdr
restarts (tested on 0.9.5). Metadata tokens are capped at 80 characters and
lost on restart. Titles, process arguments and environment are lost or
invisible.

The address is stored in herdr's session file and shown to every device. Do
not use addresses that contain secrets (for example a `?token=` URL).

## Create

1. The user types an address. A bare `host:port` gets `http://`. Only `http`
   and `https` are accepted. Addresses longer than 1024 characters are refused
   (the label's argument limit).
2. `layout.apply` makes the pane with the label `oriel:browser#<iid> <url>`
   and the placeholder command, then `pane.move` puts it in place
   ([Create](/docs/future-work/plugins/labels#create)).
3. After a later edit of the address, `pane.rename {label: "oriel:browser#<iid> <url>"}`.
   Another device's open card keeps its page until it is built again or
   **Refreshed** ([When a card reads its state](/docs/future-work/plugins/state#when-a-card-reads-its-state)).

## In herdr's TUI

The placeholder prints "Browser", the address and "Shown in Oriel" in the
middle of the pane, and draws them again when the pane is resized
(`SIGWINCH`). The TUI's border shows the label. Keys typed into the pane do
nothing ([Create](/docs/future-work/plugins/labels#create)).

## Draw

- The card header is the toolbar: Back, Forward, Reload (Stop while
  loading), the address (the host in full, the path dimmed, and the
  machine's name on a remote machine), DevTools, then the usual card buttons.
  A thin progress line runs under the header while a page loads.
- The page is inset 6 pt inside the card, so its corners stay inside the
  card's radius. Cards are never glass; the header follows the card look.
- Navigation stays inside the card (like an iframe). A link that asks for a
  new window opens in the same card. The label keeps the address the user
  typed.
- The card's browser is kept in the PaneViewRegistry, so scrolling away does
  not reload it.
- A page that fails to load shows the app's words and the machine, for
  example "Nothing answers on localhost:3001 on devbox", with **Reload**.

## DevTools

- The DevTools button (⌥⌘I) opens Chromium's DevTools for the card's page in
  their own window (CEF's `ShowDevTools`). The window closes with the card.
  No remote debugging port is open.
- **Docked DevTools** (inside the card, under or beside the page) come next.
  CEF cannot dock them on macOS: DevTools are always Chrome style, and
  docking them in a child view crashes on a CEF check. The plan: the DevTools
  page in a second child view, connected to that one page through a bridge
  of the app's own on `127.0.0.1`, with a random port and an unguessable
  path, which passes messages with `SendDevToolsMessage` and
  `AddDevToolsMessageObserver`. Before building: check whether a child view
  can load the DevTools page bundled in Chromium, or the app must ship it.
- Rejected: CEF's remote debugging port (any process on the Mac could read
  and drive every page, with its cookies).

## Viewing state on the machine

The address after in-card navigation is saved on the pane's machine, in the
same instance state file as a plugin's
([The instance state file](/docs/future-work/plugins/state#the-instance-state-file)):
`$HOME/.local/state/oriel/<session>/browser/<iid>.json`, holding
`{"url": …}`.
- Written debounced (500 ms) when a navigation ends, as for plugins. Last
  writer wins.
- Read when the card is built or on Refresh
  ([When a card reads its state](/docs/future-work/plugins/state#when-a-card-reads-its-state)).
- When it reads the file, the card opens the saved address, else the typed
  address. That address follows the load rule below.
- Editing the address writes the new label and clears the saved address.
- Simpler choice: the scroll position is not saved. Revisit when users ask.

## When a page loads by itself

Any process on a machine (a prompt-injected agent, a script) can rename a
pane to `oriel:browser#<iid> <url>` or write its state file. So:
- A page the user creates or types loads at once and approves its origin for
  that machine.
- A card built from the machine (a fresh start, another device, a card an
  agent or the herdr TUI made) loads by itself only if its origin is approved
  for that machine or on the safe list. Otherwise it shows "Open ‹url›?"
  once; **Open** approves the origin.
- Approvals are a per-device setting, kept per machine in app storage.
- The safe list: the machine's own `localhost` and `127.0.0.1` on any port
  (always), and built in `github.com`, `gitlab.com`, `bitbucket.org`,
  `developer.apple.com`, `developer.mozilla.org`, `docs.github.com`,
  `vercel.com`, `*.vercel.app` and `*.netlify.app`.
- The Settings window ([Future work](/docs/future-work#smaller-items)) lists
  the approvals and the safe list; the user can edit both.

## Remote localhost

On a remote machine, `localhost:3000` means that machine. Each machine has
its own Chromium profile (a `CefRequestContext` with its own folder), and a
remote machine's profile sends every request through that machine:

```sh
ssh -F /dev/null -S <ctl> -O forward -D 127.0.0.1:<P> <target>
```

```text
SetPreference("proxy", {mode: "fixed_servers", server: "socks5://127.0.0.1:<P>",
                        bypass_list: "<-loopback>"})
```

- `-D` makes the host's ControlMaster a SOCKS proxy on a free local port
  `<P>`. `<-loopback>` makes Chromium send `localhost` through it too (it
  sends loopback direct by default). SOCKS5 passes the host name, so the
  machine resolves it: its `localhost`, its LAN and VPN names, its
  `/etc/hosts`.
- Every port works with one forward, and the page's origin stays exactly
  `http://localhost:3000`, a secure context, so OAuth callbacks, CORS lists
  and service workers keep working. This Mac's `localhost:3000` and
  devbox's never mix, because their profiles are apart.
- Public sites in a remote machine's card also load through that machine.
  Simpler choice; revisit if heavy public sites feel slow (a PAC script could
  send only loopback and private names through the machine).
- This Mac's profile uses no proxy. Never the global profile: in the spike,
  a browser in it followed another profile's proxy.
- The proxy setting is saved in the profile, so the app sets it (or `direct`)
  each time it creates the profile.
- The forward starts with the machine's first browser card and ends with its
  last (`ssh -O cancel`). It uses no [SSH session](/docs/machines#ssh-sessions).
  It needs `AllowTcpForwarding yes` on the server (the default). If a server
  refuses, the card says "‹machine› does not allow port forwarding".
- Checked: `-O forward -D`, `-O forward -L` and `-W` work on a master started
  with `ClearAllForwardings=yes` (OpenSSH 10.3). Chrome 156 sent loopback
  through the proxy with `<-loopback>` and kept `isSecureContext` true.
- **iPhone and iPad** ([iPhone and iPad](/docs/future-work/iphone-and-ipad)):
  WebKit, so an in-app listener on `127.0.0.1:<P>` pipes each connection it
  accepts into a Citadel `direct-tcpip` channel, one port at a time.
  Listeners stop when the app goes to the background, like terminal streams,
  and start again on return.

## Finding ports

- **Open :‹port› chip:** when a frame arrives for a terminal card of the
  selected tab, the app searches the screen text it already holds for
  `https?://(localhost|127\.0\.0\.1|0\.0\.0\.0|\[::1\]):[0-9]+`. A match
  shows "Open :3000" on that terminal's card. A click makes a browser pane
  for that address next to it.
- **Ports list:** the picker's Browser entry lists the machine's listening
  ports. It runs `ss -ltnH` (Linux) or `lsof -nP -iTCP -sTCP:LISTEN` (macOS)
  once when the list opens, never on a timer.

## Other rules

- Pages are told the current `prefers-color-scheme`, which follows the
  app's appearance (D44).
- When a page's renderer ends (`OnRenderProcessTerminated`), the card loads
  the page again.
- ⌘L focuses the address in the header; ⌘F finds in the page. CEF's
  `OnPreKeyEvent` passes the app's shortcuts to the menu while the page has
  focus.
- When the command palette's query is an address, its top row is "Open in
  Browser": a browser pane beside the keyboard card.
- Page dialogs show as a sheet on the card, labeled with the origin.
- Closing a browser pane never asks, because it runs only its placeholder.
- After a cold restart the pane returns as a plain shell with its label, so
  the page still draws ([Create](/docs/future-work/plugins/labels#create)).
- Memory: about 200–280 MB for the first page (all of Chromium's
  processes), 70–80 MB for each more page, and about 300 MB more while
  DevTools are open (measured with CEF 156). The shared cap of live web views
  holds ([Plugin UI](/docs/future-work/plugins/plugin-ui#risks)).

## Risks

| Risk | Effect | Plan |
|---|---|---|
| Labels or state files written by a hostile machine | a page opens by itself | an origin outside the approvals and the safe list needs a click ([When a page loads by itself](#when-a-page-loads-by-itself)) |
| CEF's browser process runs in the app | an engine crash ends the app | an exact pin, reviewed updates; watch crash reports |
| A late engine update | known Chromium security holes stay open | a bump each CEF release, or CEF's long-term branch |
| The SOCKS port is open to other accounts on the Mac | another account can reach the machine's network | accepted for a single-user Mac; a random port, open only while a card needs it |
| A server with `AllowTcpForwarding no` | remote `localhost` pages cannot load | the card says so; Tailscale or LAN addresses still load; a bigger server helper later |
| SwiftUI's own application class is replaced by CEF's subclass | undocumented; may break on a macOS update | checked on each macOS release |
| App size (+330 MB) and memory | a bigger download; memory growth | the shared cap of live web views; later, download the engine on first use |

## Choices

- **Chromium through CEF on the Mac.** Chrome DevTools in the app, the page
  as Chrome draws it, and a proxy per profile that carries loopback.
  Rejected: WKWebView with Safari's Web Inspector (not Chrome DevTools;
  docking it needs private API); real Chrome driven over the DevTools
  protocol (screencast frames, no IME); off-screen rendering (the app would
  redo input, IME and accessibility); a Chromium build of our own (a team's
  work); CefSwift, a pure Swift wrapper (about 8,000 lines from one author;
  watch it).
- **A built-in pane kind with one profile per machine**, and the load rule
  above. No request leaves the device for an unknown origin without the user,
  and machines stay apart. Rejected: loading every label by itself; tracking
  which device created or edited a label; a two-part rule for the saved
  address.
- **Remote pages through a SOCKS forward per machine.** One forward covers
  every port and name on the machine, the origin stays exact, and nothing is
  installed there. Rejected: a forward per port (port clashes between
  machines, a navigation decider); a server helper of our own now;
  `pane.output_matched` on a second event stream.
- **The typed address in the label, the current one in the state file.**
  Coming back to a browser card, on any device or after a restart, shows the
  page where the user left it, with one state path for every card. Rejected:
  rewriting the label on every navigation (a rename per click, seen by every
  TUI); state kept per device in the app.
