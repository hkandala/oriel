Not built. This page is the design ([Pane kinds and plugins](/docs/future-work/plugins)).
Research and spikes:
[`browser.md`](https://github.com/hkandala/oriel/blob/main/resources/research/plugins/browser.md).

herdr cannot draw a web page. So a herdr pane holds the place in the layout,
and the app draws a web view in its rectangle. The browser is the first pane
kind built on the [plugin foundation](/docs/future-work/plugins#the-first-slice),
and it is built into the app.

## The engine

- Each card holds one `WKWebView` with a `WKUIDelegate`, wrapped for SwiftUI
  ([Plugin UI](/docs/future-work/plugins/plugin-ui)). WebKit is part of
  macOS and iOS, so the app grows by nothing.
- The page gets no bridge: no `window.oriel`, no script message handlers.
- **Web Inspector** opens in its own window: the card's DevTools button
  (⌥⌘I) shows WebKit's inspector for that page. Every browser card sets
  `isInspectable`, so Safari's Develop menu (Develop › ‹this Mac› › Oriel)
  reaches the page too. Showing the inspector from a button has no public API;
  the button calls WebKit's `_WKInspector` `show` (cmux ships the same).
  Before building: check that `show` opens the window in the running app (a
  spike app in the background got the inspector object, but no window).

## The marker is the pane label

The label is the marker: `oriel:browser#<iid> <url>`, for example
`oriel:browser#m4p8sa http://localhost:3000/dashboard`
([Labels and instance ids](/docs/future-work/plugins/labels)). The label is
the only pane field that has no length limit and survives moves and herdr
restarts (tested on 0.9.5). Metadata tokens are capped at 80 characters and
lost on restart. Titles, process arguments and environment are lost or
invisible.

The address in the label is as the machine sees it: `localhost` means the
pane's machine ([Remote localhost](#remote-localhost)). It is stored in
herdr's session file and shown to every device. Do not use addresses that
contain secrets (for example a `?token=` URL).

## Create

1. The user types an address. A bare `host:port` gets `http://`. Only `http`
   and `https` are accepted. Addresses longer than 1024 characters are refused
   (the label's argument limit).
2. `layout.apply` makes the pane with the label `oriel:browser#<iid> <url>`
   and the placeholder command, then `pane.move` puts it in place
   ([Create](/docs/future-work/plugins/labels#create)).
3. After a later edit of the address, `pane.rename {label: "oriel:browser#<iid> <url>"}`.
   Another device's open card keeps its page until it is built again or
   **Refreshed** ([When a card reads its state](/docs/future-work/plugins/state#when-a-card-reads-its-state)).

## In herdr's TUI

The placeholder prints "Browser", the address and "Shown in Oriel" in the
middle of the pane, and draws them again when the pane is resized
(`SIGWINCH`). The TUI's border shows the label. Keys typed into the pane do
nothing ([Create](/docs/future-work/plugins/labels#create)).

## Draw

- The card header is the toolbar: Back, Forward, Reload (Stop while
  loading), the address (the host in full, the path dimmed, and the
  machine's name on a remote machine), DevTools, then the usual card buttons.
  A thin progress line runs under the header while a page loads.
- The page is inset 6 pt inside the card, so its corners stay inside the
  card's radius. Cards are never glass; the header follows the card look.
- Navigation stays inside the card (like an iframe). A link that asks for a
  new window opens in the same card. The label keeps the address the user
  typed.
- The card's web view is kept in the PaneViewRegistry, so scrolling away
  does not reload it.
- A page that fails to load shows the app's words and the machine, for
  example "Nothing answers on localhost:3001 on devbox", with **Reload**.
- A floated browser pane ([Floating pane](/docs/ui/window#floating-pane))
  keeps the same toolbar under the floating window's title row.

## Viewing state on the machine

The address after in-card navigation is saved on the pane's machine, in the
same instance state file as a plugin's
([The instance state file](/docs/future-work/plugins/state#the-instance-state-file)):
`$HOME/.local/state/oriel/<session>/browser/<iid>.json`, holding
`{"url": …}`, as the machine sees it.
- Written debounced (500 ms) when a navigation ends, as for plugins. Last
  writer wins.
- Read when the card is built or on Refresh
  ([When a card reads its state](/docs/future-work/plugins/state#when-a-card-reads-its-state)).
- When it reads the file, the card opens the saved address, else the typed
  address. That address follows the load rule below.
- Editing the address writes the new label and clears the saved address.
- Simpler choice: the scroll position is not saved. Revisit when users ask.

## When a page loads by itself

Any process on a machine (a prompt-injected agent, a script) can rename a
pane to `oriel:browser#<iid> <url>` or write its state file. So:
- A page the user creates or types loads at once and approves its origin for
  that machine.
- A card built from the machine (a fresh start, another device, a card an
  agent or the herdr TUI made) loads by itself only if its origin is approved
  for that machine or on the safe list. Otherwise it shows "Open ‹url›?"
  once; **Open** approves the origin.
- Approvals are a per-device setting, kept per machine in app storage.
- The safe list: the machine's own `localhost` and `127.0.0.1` on any port
  (always), and built in `github.com`, `gitlab.com`, `bitbucket.org`,
  `developer.apple.com`, `developer.mozilla.org`, `docs.github.com`,
  `vercel.com`, `*.vercel.app` and `*.netlify.app`.
- The Settings window ([Future work](/docs/future-work#smaller-items)) lists
  the approvals and the safe list; the user can edit both.

## Profiles

Each machine has its own `WKWebsiteDataStore(forIdentifier:)`, with the
machine's id from the machine list as its identifier (This Mac has a fixed
one).
- The store keeps cookies, local storage, IndexedDB, the cache and service
  workers on disk, under `~/Library/WebKit/<bundle id>/WebsiteDataStore/<id>/`,
  across relaunches. Logins persist, and machines stay apart.
- Stores are per device: another Mac or the iPhone has its own logins.
- Removing a machine removes its store (`WKWebsiteDataStore.remove(forIdentifier:)`).
- `proxyConfigurations` belongs to the store and is not saved: the app sets
  it each time it makes the store, before the first load.
- WebKit uses no keychain item for cookies or storage, so no keychain prompt
  appears (checked with stores that set cookies).

## Remote localhost

On a remote machine, `localhost:3000` means that machine. One SOCKS forward
per machine carries every page of that machine's cards:

```sh
ssh -F /dev/null -S <ctl> -O forward -D 127.0.0.1:<P> <target>
```

- `-D` makes the host's ControlMaster a SOCKS proxy on a free local port
  `<P>`. Each connection to it becomes a channel on the existing SSH
  connection, and the server connects to the host and port the page asked
  for. The machine's store gets
  `ProxyConfiguration(socksv5Proxy: 127.0.0.1:<P>)`.
- Each machine has its own `<P>`. The page's port (3000) travels inside each
  SOCKS request, so devbox's `:3000` and another machine's `:3000` never
  compete for a port on the Mac.
- **WebKit never sends `localhost`, `127.0.0.1` or `[::1]` through a proxy**
  (checked; `matchDomains` does not change it). So a remote card loads
  `http://<machine>.localhost:3000` where the machine sees
  `http://localhost:3000`. WebKit sends that name through the proxy and
  treats it as a secure context, and the machine resolves `*.localhost` to its
  own loopback (macOS and Linux with systemd do). Checked end to end.
- `<machine>` is the machine's name in lowercase letters, digits and dashes
  (made unique in the list). The address field and the label show the
  machine's view (`localhost:3000`) with the machine's name beside it.
- Each machine's pages have their own origins (`devbox.localhost:3000`) and
  their own store, so nothing of two machines mixes.
- Simpler choice: the origin is `devbox.localhost:3000`, not `localhost:3000`.
  OAuth callbacks and CORS lists need that name added; Vite allows
  `*.localhost` by default. Revisit if dev servers refuse it often.
- A machine that cannot resolve `*.localhost` shows "‹machine› cannot reach
  ‹name›". A fix then is a small SOCKS listener of the app's own that maps
  `*.localhost` to `localhost` and dials through `ssh -W`.
- Public sites in a remote machine's card also load through that machine.
  Simpler choice; revisit if they feel slow.
- This Mac's store uses no proxy.
- The forward starts with the machine's first browser card and ends with its
  last (`ssh -O cancel`). It uses no [SSH session](/docs/machines#ssh-sessions).
  It needs `AllowTcpForwarding yes` on the server (the default). If a server
  refuses, the card says "‹machine› does not allow port forwarding".
- Checked: `-O forward -D`, `-O forward -L` and `-W` work on a master started
  with `ClearAllForwardings=yes` (OpenSSH 10.3).
- **iPhone and iPad** ([iPhone and iPad](/docs/future-work/iphone-and-ipad)):
  an in-app SOCKS listener on `127.0.0.1:<P>` pipes each connection it
  accepts into a Citadel `direct-tcpip` channel. Listeners stop when the app
  goes to the background, like terminal streams, and start again on return.

## Finding ports

- **Open :‹port› chip:** when a frame arrives for a terminal card of the
  selected tab, the app searches the screen text it already holds for
  `https?://(localhost|127\.0\.0\.1|0\.0\.0\.0|\[::1\]):[0-9]+`. A match
  shows "Open :3000" on that terminal's card. A click makes a browser pane
  for that address next to it.
- **Ports list:** the picker's Browser entry lists the machine's listening
  ports. It runs `ss -ltnH` (Linux) or `lsof -nP -iTCP -sTCP:LISTEN` (macOS)
  once when the list opens, never on a timer.

## Agents

The first slice gives agents no control of browser cards. An agent that
needs a browser runs its own on its machine (Playwright, chrome-devtools-mcp),
next to the dev server. WKWebView has no automation protocol, and
`safaridriver` drives only Safari. A later design could let an agent ask the
app, through a pane metadata token, to read, run script in or capture one
browser card it is allowed to, with the result written back to a file on the
machine; it needs its own consent design
([Changes panel](/docs/future-work/changes-panel)).

## Other rules

- Pages are told the current `prefers-color-scheme`, which follows the
  app's appearance (D44).
- The web view's user agent ends with `Version/18.0 Safari/605.1.15`
  (`applicationNameForUserAgent`), so sites that sniff for Safari work.
- When the page's process ends (`webViewWebContentProcessDidTerminate`),
  the card loads the page again.
- ⌘L focuses the address in the header; ⌘F finds in the page with
  `WKWebView`'s find.
- When the command palette's query is an address, its top row is "Open in
  Browser": a browser pane beside the keyboard card.
- Page dialogs show as a sheet on the card, labeled with the origin.
- Plain `http` needs `NSAllowsArbitraryLoadsInWebContent` and
  `NSAllowsLocalNetworking`.
- Closing a browser pane never asks, because it runs only its placeholder.
- After a cold restart the pane returns as a plain shell with its label. The
  app knows the pane by its label alone, builds the card again and reads the
  state file ([Create](/docs/future-work/plugins/labels#create)).

## Risks

| Risk | Effect | Plan |
|---|---|---|
| Labels or state files written by a hostile machine | a page opens by itself | an origin outside the approvals and the safe list needs a click ([When a page loads by itself](#when-a-page-loads-by-itself)) |
| The SOCKS port is open to other accounts on the Mac | another account can reach the machine's network | accepted for a single-user Mac; a random port, open only while a card needs it |
| A server with `AllowTcpForwarding no` | remote `localhost` pages cannot load | the card says so; Tailscale or LAN addresses still load; a bigger server helper later |
| `_WKInspector` is private | the DevTools button may break on a macOS update | Safari's Develop menu still reaches every card |
| Web view memory | memory growth | the shared cap of live web views ([Plugin UI](/docs/future-work/plugins/plugin-ui#risks)) |

## Choices

- **WKWebView with Web Inspector in its own window.** No size cost, the same
  engine as plugin cards and iOS, and a proxy per store. Considered: Chromium
  through CEF, for Chrome DevTools. It worked in a spike (a SwiftUI host, a
  314-line Objective-C++ shim, a profile and SOCKS proxy per machine), but it
  adds 330 MB to the app, uses 195–281 MB for the first page and about
  300 MB more with DevTools open, needs an engine update about every 4 weeks,
  runs Chromium's browser process inside the app, cannot dock DevTools on
  macOS, and its shared "Chromium Safe Storage" keychain item held every
  request behind a password prompt. Rejected: real Chrome driven over its
  DevTools protocol (screencast frames, no IME); a Chromium build of our own.
- **A built-in pane kind with one store per machine**, and the load rule
  above. No request leaves the device for an unknown origin without the user,
  and machines stay apart. Rejected: loading every label by itself; tracking
  which device created or edited a label; a two-part rule for the saved
  address.
- **Remote pages through a SOCKS forward per machine.** One forward covers
  every port and name on the machine, and nothing is installed there.
  Rejected: a forward per port (ports clash between machines and with the
  Mac, and a page's links need a navigation decider); a server helper of our
  own now; `pane.output_matched` on a second event stream.
- **The typed address in the label, the current one in the state file.**
  Coming back to a browser card, on any device or after a restart, shows the
  page where the user left it, with one state path for every card. Rejected:
  rewriting the label on every navigation (a rename per click, seen by every
  TUI); state kept per device in the app.
