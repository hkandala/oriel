A plugin is a small web page: HTML, CSS and JavaScript. Each plugin card is a
native web view (a `WKWebView` with a `WKUIDelegate`, wrapped for SwiftUI)
that loads the plugin's own files. A bridge gives the page `run(argv)` and `dial(host, port)` on the
pane's machine, plus a few app calls ([Plugin API](/docs/future-work/plugins/api)).

## How it works

How a plugin card loads:

1. The plugin's own files (`index.html` and the rest) are served from the app
   through a URL scheme, `oriel-plugin://<id>/`.
2. Each card gets its own `WKWebView`. The app injects `window.oriel` before
   the page runs.
3. The web view is drawn in the card, in the strip.

How the page reaches its machine:

1. The page calls `oriel.run` or `oriel.dial`.
2. The bridge (Swift) checks the card's machine.
3. `Exec` runs the command or opens the stream on that machine. On a remote
   machine a run goes over the relay and a dial through `ssh -W`
   ([Run and dial](/docs/future-work/plugins#run-and-dial)).
4. The result comes back as a promise in the page.

- The app serves the plugin's files from a custom URL scheme,
  `oriel-plugin://<id>/`. Nothing loads from the network.
- Before the page runs, the app injects `window.oriel` (the API) and a small
  stylesheet with the app's colors and fonts as CSS variables, so plugins can
  match the cards around them. Pages are told the current `prefers-color-scheme`, which follows the
  app's appearance (D44), and the CSS variables follow the style and
  appearance.
- Any JavaScript works: plain DOM, React, Svelte or anything else, bundled by
  the author. The app runs no build step.
- Browser cards use the same web view type, with no bridge and one data
  store per machine ([Browser](/docs/ui/browser)). SwiftUI's own `WebPage` is not used: it has no new-window hook, so it drops `window.open` silently
  ([Plugin security](/docs/future-work/plugins/security)).
- WebKit is built into macOS and iOS, so the same plugin can run on an
  [iPhone and iPad app](/docs/future-work/iphone-and-ipad#plugins) too.
- A web view costs about 50 MB empty and 120–200 MB in use. The app will keep
  at most 6 live web views on the Mac, browser and plugin cards together,
  least recently used first out. An evicted card keeps an image of its last
  frame. Browser cards have no cap yet.
- The card header has a plugin|term switch, which shows the pane's
  placeholder terminal, and **Refresh**
  ([When a card reads its state](/docs/future-work/plugins/state#when-a-card-reads-its-state)).

## Checks before building

- 6 live plugin cards plus 9 terminals in the strip hold frame time and stay
  under the memory budget.
- The content rule and the Content Security Policy block every load and
  script that is not the plugin's own, and `window.oriel` is in place before
  the page's first script.
- The page's message handlers sit behind a weak proxy, so a closed card's web
  view is freed.

## Risks

| Risk | Effect | Plan |
|---|---|---|
| Plugin HTML built from repository text | a script in a repository file runs in the plugin page | the Content Security Policy allows only the plugin's own scripts; core plugins insert text, not HTML |
| A malicious plugin the user installed | anything the user can do on machines where its panes open | the consent sheet in plain words, the This Mac confirm, the source shown and pinned to a commit ([Plugin security](/docs/future-work/plugins/security)) |
| Web view memory (120–200 MB each) | memory growth | at most 6 live web views, browser and plugin cards together; evict on memory pressure |
| Third-party code in the app | updates lag; supply chain | exact pins, reviewed updates (as for libghostty-spm today) |

## Options we compared

| Option | Pros | Cons |
|---|---|---|
| **A web page in a native web view** (chosen) | any web library; custom drawing (SVG, canvas) is free; Safari Web Inspector; one engine on macOS and iOS; little app code | 120–200 MB per live card; looks like the app only if the author uses its CSS variables; HTML built from repository text needs care ([Plugin security](/docs/future-work/plugins/security)) |
| TypeScript + React drawn as native SwiftUI: React against our own component kit (`List`, `Detail`, `Diff`, `Form`), one JavaScriptCore VM per card (Raycast 1.x's model) | truly native; ~3 MB per card | our own component kit, reconciler and build tool to keep; plugins get only our components. Measured in [`plugins.md`](https://github.com/hkandala/oriel/blob/main/resources/research/plugins/plugins.md#how-to-draw-plugin-ui); revisit when web plugins look or feel wrong next to native cards |
| React Native embedded | React to native | two forks to keep in step, a large dependency |
| Native Swift plugins | fully native | impossible on iOS; runs inside our process with our SSH connections |
| Apple ExtensionKit | sandboxed native views | iOS hosts only extensions inside our own app |

- Plugins cannot claim the app's shortcuts
  ([Keyboard shortcuts](/docs/ui/theme-and-accessibility#keyboard-shortcuts)):
  keys go to the main menu first.
