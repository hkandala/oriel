Not built. Today a new tab or split is always a terminal. The pages in this
section are the design for the pane picker, the Agent and Web page kinds, and
plugins.

A pane kind is what a pane shows: a terminal, an agent, a web page or a
plugin. One picker makes every pane kind. Terminal, Agent and Web page are
built into the app. Every other pane kind is a plugin: a small web page
([Plugin UI](/docs/future-work/plugins/plugin-ui)) from one plugin registry.

| Pane kind | Kind | UI | JavaScript | How herdr marks the pane |
|---|---|---|---|---|
| Terminal | built in | native terminal (libghostty) | none | none (the default) |
| Agent | built in | native terminal + chat view ([Chat view](/docs/future-work/chat-view)) | none | none (herdr sets `pane.agent`) |
| Web page | built in | native web view ([Web page](/docs/future-work/web-page)) | none (only the page's own) | label `oriel:web#<iid> <url>` |
| `git-history`, `diff`, `markdown` | core | a web page in a native web view | yes, the public API | label `oriel:…` ([Labels and instance ids](/docs/future-work/plugins/labels)) |
| your plugins | installed | a web page in a native web view | yes, the public API | label `oriel:…` |

- Core plugins ship with the app. They use exactly the public API and are
  reference code for plugin authors.
- A web or plugin pane is a real herdr pane with a label. In herdr it runs a
  quiet placeholder command, so herdr TUI users see what the pane is. The
  placeholder is cosmetic: the label is the truth
  ([Labels and instance ids](/docs/future-work/plugins/labels)).
- herdr's own TUI plugins are not part of this system. A pane that a herdr
  plugin opened shows as a terminal, because it is one.

## The picker

`+` in the tab bar and a split open the picker. Its header names the
machine ("New pane on devbox").

- The fixed rows come first: Terminal, Agent ▸ (one row per available agent,
  [Agent](/docs/future-work/plugins/agent#agent)) and Web page (an address
  field and the machine's listening ports,
  [Finding ports](/docs/future-work/web-page#finding-ports)).
- Then a "Plugins" header and one row per plugin pane kind from the
  manifests: core plugins first,
  then linked and installed ones. A plugin whose pane needs an argument asks
  for it before the pane is made
  ([Manifest](/docs/future-work/plugins/packages#manifest)).
- The app calls herdr only after the user picks. Until then nothing changes
  in herdr.

## Run and dial

Web pages and plugins reach their pane's machine through two calls on its
`Exec`. The app has the first one today
([Running commands](/docs/talking-to-herdr#running-commands)); the second
is new:

```swift
/// Run argv on the machine; stdin, stdout and the exit status come back.
func run(_ argv: [String]) async throws -> Channel
/// Open a TCP stream to host:port, as seen from the machine (not built).
func dial(host: String, port: Int) async throws -> Channel
```

- **`run`** is a `Process` on This Mac. On a remote machine it goes through
  the relay: one SSH session carries every run. Closing a run's stdin ends
  it.
- **`dial`** on This Mac is a plain TCP connection. On a remote machine it is
  `ssh -S <ctl> -W <host>:<port> <target>` on the host's ControlMaster, with
  the same `-F /dev/null -o ControlMaster=no -o BatchMode=yes` options as a
  run, so a missing master never prompts: one process, one stream on its
  stdio. It opens a forwarding channel, not an SSH session, so the server's
  `MaxSessions` (its limit on sessions per connection) does not count it. It
  needs `AllowTcpForwarding yes` on the server (the default). Check first that
  `-W` and `-O forward` work on a master started with
  `ClearAllForwardings=yes` ([The SSH connection](/docs/machines#the-ssh-connection)).
- `dial` needs a `Channel` that carries bytes; today a `Channel` gives lines.
- A web card needs a local port, not a stream:
  [Remote localhost](/docs/future-work/web-page#remote-localhost).
- Nothing of ours is installed on the machine: `sshd`, POSIX tools and herdr
  do the work. A bigger helper would sit behind the same `run` and `dial` calls
  ([Future work](/docs/future-work#smaller-items)).

## Where it lives

- `PluginRegistry`: core, linked and installed plugins, their manifests and
  consent.
- `PluginHost`: one web page per plugin card, and the bridge
  (`window.oriel`) to `run`, `dial` and the API; every call checks the card's
  machine in Swift.
- `HerdrKit` gets the label parser, the state-file write command and the
  transcript parsers, each with unit tests. `SSHExec` gets `dial`.
- The `PaneViewRegistry` owns web and plugin cards as it owns terminal views,
  so scrolling never destroys them.
- App storage (`UserDefaults`): consent and This Mac answers per plugin id
  and source, plugin preferences (passwords in the Keychain), and approved
  web origins per machine with the safe list. Plugin code and its source
  record live in `~/Library/Application Support/Oriel/plugins/`.

## Choices

- **One picker, one registry.** The three built-in kinds are special
  everywhere else (streams, chat, labels); one model covers the rest.
  Rejected: native manifests for the built-in kinds (a `native` field,
  reserved ids), and herdr TUI plugins in the picker.
- **Plugins live in the app**, installed from a git URL or a linked folder,
  already built; the app never runs npm
  ([Packages](/docs/future-work/plugins/packages)). One install per Mac covers
  every machine, and no machine needs setup. Rejected: herdr plugins on each
  machine; an in-app store.
