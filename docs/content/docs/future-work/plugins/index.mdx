Terminal, Agent and Browser are built in
([New pane](/docs/ui/new-pane), [Browser](/docs/ui/browser)), and so are five
default plugins: File, Preview, Markdown, Diff and Files
([Default plugins](/docs/ui/plugins)). Plugins that the user installs are not
built. The pages in this section are their design, on the foundation that
the browser and the default plugins built ([What is built](#what-is-built)).

A pane kind is what a pane shows: a terminal, an agent, a browser or a
plugin. Terminal, Agent and Browser are
built into the app. Every other pane kind is a plugin: a small web page
([Plugin UI](/docs/future-work/plugins/plugin-ui)) from one plugin registry.

| Pane kind | Kind | UI | JavaScript | How herdr marks the pane |
|---|---|---|---|---|
| Terminal | built in | native terminal (libghostty) | none | none (the default) |
| Agent | built in | native terminal + chat view ([Chat view](/docs/ui/chat-view)) | none | none (herdr sets `pane.agent`) |
| Browser | built in | native web view ([Browser](/docs/ui/browser)) | none (only the page's own) | label `oriel:browser#<iid> <url>` |
| File, Preview, Markdown, Diff, Files | built in ([Default plugins](/docs/ui/plugins)) | a web page from the app's bundle in a native web view | yes, with a fixed bridge, not the public API | label `oriel:<kind>#<iid> <arg>` |
| core plugins | core | a web page in a native web view | yes, the public API | label `oriel:…` ([Labels and instance ids](/docs/future-work/plugins/labels)) |
| your plugins | installed | a web page in a native web view | yes, the public API | label `oriel:…` |

- Core plugins ship with the app. They use exactly the public API and are
  reference code for plugin authors.
- A browser or plugin pane is a real herdr pane with a label. In herdr it runs a
  quiet placeholder command, so herdr TUI users see what the pane is. The
  placeholder is cosmetic: the label is the truth
  ([Labels and instance ids](/docs/future-work/plugins/labels)).
- herdr's own TUI plugins are not part of this system. A pane that a herdr
  plugin opened shows as a terminal, because it is one.

## Choosing a kind

Every new pane shows the [New pane](/docs/ui/new-pane) chooser with the
built-in kinds: Terminal, Agent, Browser, Files and Changes. Its commands
(Open Terminal Here, Start Agent Here, Open Browser Here, Open Files Here,
Open Changes Here) change a pane's kind later.

- Plugin kinds join the chooser when plugins are built: one more option that
  lists the plugin pane kinds from the manifests, core plugins first, then
  linked and installed ones. A plugin whose pane needs an argument asks for it
  before the pane is made
  ([Manifest](/docs/future-work/plugins/packages#manifest)).

## Run and dial

Browser panes and plugins reach their pane's machine through two calls on its
`Exec`. The app has the first one today
([Running commands](/docs/talking-to-herdr#running-commands)); the second
is new:

```swift
/// Run argv on the machine; stdin, stdout and the exit status come back.
func run(_ argv: [String]) async throws -> Channel
/// Open a TCP stream to host:port, as seen from the machine (not built).
func dial(host: String, port: Int) async throws -> Channel
```

- **`run`** is a `Process` on This Mac. On a remote machine it goes through
  the relay: one SSH session carries every run. Closing a run's stdin ends
  it.
- **`dial`** on This Mac is a plain TCP connection. On a remote machine it is
  `ssh -S <ctl> -W <host>:<port> <target>` on the host's ControlMaster, with
  the same `-F /dev/null -o ControlMaster=no -o BatchMode=yes` options as a
  run, so a missing master never prompts: one process, one stream on its
  stdio. It opens a forwarding channel, not an SSH session, so the server's
  `MaxSessions` (its limit on sessions per connection) does not count it. It
  needs `AllowTcpForwarding yes` on the server (the default). `-W` and
  `-O forward` work on a master started with `ClearAllForwardings=yes`
  ([The SSH connection](/docs/machines#the-ssh-connection);
  [evidence](https://github.com/hkandala/oriel/blob/main/resources/research/plugins/plugins.md#how-plugins-reach-a-remote-machine)).
- `dial` needs a `Channel` that carries bytes; today a `Channel` gives lines.
- A browser card uses a SOCKS proxy per machine, not a stream:
  [Remote localhost](/docs/ui/browser#remote-localhost).
- Nothing of ours is installed on the machine: `sshd`, POSIX tools and herdr
  do the work. A bigger helper would sit behind the same `run` and `dial` calls
  ([Future work](/docs/future-work#smaller-items)).

## Where it lives

- `PluginRegistry`: core, linked and installed plugins, their manifests and
  consent (not built).
- One web page per plugin card, and the bridge (`window.oriel`) to `run`,
  `dial` and the API; every call checks the card's machine in Swift. The
  default plugins' `WebCard` and `oriel-plugin://` scheme are built, with a
  fixed bridge in place of `window.oriel`.
- `HerdrKit` has the label parser and the default plugins' `Files` and `Git`.
  It gets the state-file write command for plugins and the transcript
  parsers. `SSHExec` gets `dial`.
- The `PaneViewRegistry` owns browser and plugin cards as it owns terminal
  views, so scrolling never destroys them (built).
- App storage (`UserDefaults`): consent and This Mac answers per plugin id
  and source, plugin preferences (passwords in the Keychain), and approved
  browser origins per machine (built). Plugin code and its source
  record live in `~/Library/Application Support/Oriel/plugins/`. Browser
  cards keep one WebKit data store per machine.

## What is built

The default plugins are five more pane kinds on this design, built into the
app ([Default plugins](/docs/ui/plugins)). They have `oriel:<kind>` labels
for any kind with one placeholder, the chooser's Files and Changes, linked
opens into a new tab, a web page per card served from `oriel-plugin://` under
a Content Security Policy with a navigation lock, and a fixed bridge of asks
and reports ([How the web cards work](/docs/ui/plugins#how-the-web-cards-work)).
They keep no state file. Their pages are the app's own, not plugins on the
public API.

The browser is built into the app too: nothing to install, enable or
disable, and its page gets no bridge (no `window.oriel`, so no `run`). It has
the parts every later kind needs:
- the label grammar and its parser (HerdrKit's `PaneLabel`), the instance id,
  and restore by label
  ([Labels and instance ids](/docs/future-work/plugins/labels));
- the placeholder pane made with `layout.apply` and `pane.move`;
- the chooser's Browser option and Open Browser Here;
- the instance state file: read when a card is built, written 500 ms after a
  change, removed on close, and the 30-day cleanup on connect
  ([State and restore](/docs/future-work/plugins/state));
- the load rule and the approvals per machine.

Not built yet: **Refresh**, the cap of live web views, and the manifest value
for a built-in kind. The browser and the default plugins call their labels
(and the browser its state file) from Swift.
Plugins get them as calls: their pane context (machine, session, iid,
argument, cwd), `setArg`, `state.get` and `state.set`, and `run`, as
`window.oriel` ([Plugin API](/docs/future-work/plugins/api)). A built-in kind
will be declared with the fields a manifest uses
([Manifest](/docs/future-work/plugins/packages#manifest)):

```json
{ "id": "browser", "title": "Browser", "icon": "globe",
  "arg": { "title": "Address", "placeholder": "localhost:3000", "required": false } }
```

Later: `dial`, the snapshot event, preferences, packages, consent and plugin
cards.

## Choices

- **One chooser, one registry.** The three built-in kinds are special
  everywhere else (streams, chat, labels); one model covers the rest.
  Rejected: native manifests for the built-in kinds (a `native` field,
  reserved ids), and herdr TUI plugins in the chooser.
- **Plugins live in the app**, installed from a git URL or a linked folder,
  already built; the app never runs npm
  ([Packages](/docs/future-work/plugins/packages)). One install per Mac covers
  every machine, and no machine needs setup. Rejected: herdr plugins on each
  machine; an in-app store.
