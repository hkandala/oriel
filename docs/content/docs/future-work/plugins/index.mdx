<Callout title="Proposed design" type="warn">
This section is a proposal, not yet approved. The two default plugins, File
Explorer and Git, work today as [Default plugins](/docs/ui/plugins)
describes, with a fixed bridge. The memory budget below is built
([What stays in memory](/docs/ui/browser#what-stays-in-memory)).
Nothing on these pages is built until the user approves it. Then each part
moves to the pages of the built app.
</Callout>

A pane kind is what a pane shows: a terminal, an agent, a browser or a
plugin. Terminal and Agent are herdr's own panes. Every other kind is a
plugin: a herdr pane that runs a placeholder, with a label that names the
plugin ([Labels and instance ids](/docs/future-work/plugins/labels)). The app
draws the plugin's card over that pane.

In this design every plugin is written the same way:
- A plugin is a folder with a `manifest.json` and a TypeScript entry file
  (`main.ts`), plus any other files it imports
  ([Manifest](/docs/future-work/plugins/manifest)).
- Oriel bundles the folder with esbuild, a bundler that ships inside the app.
  It builds a plugin when it loads it and again when a file in the folder
  changes ([Build a plugin](/docs/future-work/plugins/building)).
- Each card is a web view of its own. Its page calls the app through one
  typed object, `oriel`
  ([Plugin API](/docs/future-work/plugins/api)).
- The two default plugins (File Explorer and Git) become
  plugins in this format that ship inside the app. They use the same API as
  any other plugin.
- The browser stays a native web view, and it is a kind in the same model
  ([Browser and native kinds](/docs/future-work/plugins/browser-and-native)).

| Pane kind | Content | Its code | How herdr marks the pane |
|---|---|---|---|
| Terminal | native terminal (libghostty) | the app | none (the default) |
| Agent | native terminal and chat view | the app | none (herdr sets `pane.agent`) |
| Browser | native web view of any site | the app | label `oriel:browser#<iid> <url>` |
| File Explorer, Git | a plugin page in a web view | plugin folders inside the app | label `oriel:<id>#<iid> <arg>` |
| your plugins | a plugin page in a web view | plugin folders on This Mac | label `oriel:<id>#<iid> <arg>` |

## How the pieces connect

```text
~/.config/oriel/plugins/csv-table/     manifest.json, main.ts, table.css
        │  esbuild (in the app), on load and on every change
        ▼
~/Library/Caches/oriel/plugins/csv-table/<build>/    main.js, main.css
        │  served as oriel-plugin://csv-table/
        ▼
WKWebView, one per card ── the app's runtime puts `oriel` in the page
        │  oriel.files.read(path) as a bridge message
        ▼
the bridge (Swift) ── checks the manifest's permissions
        │  Exec of the card's machine
        ▼
This Mac, or a remote machine over the relay
```

1. The registry reads every `manifest.json`: the plugins inside the app
   first, then the ones in the user's folder.
2. A card of a user plugin needs a build. esbuild turns `main.ts` and what it
   imports into `main.js` in the app's cache, in tens of milliseconds.
3. The scheme handler serves that folder as `oriel-plugin://<id>/` under a
   strict Content Security Policy
   ([Plugin security](/docs/future-work/plugins/security)).
4. Before the page runs, the app adds its runtime. The runtime makes the
   `oriel` object, and the app's loader calls the plugin's default export
   with it.
5. Each call of the page is a bridge message. Swift checks it against the
   manifest's permissions and runs it with the card's machine's `Exec`.

## Where things live

| What | Where |
|---|---|
| The default plugins' source | `web/plugins/<id>/` in the repository, built by `make web` into the app's `Resources/plugins/` |
| Your plugins | `~/.config/oriel/plugins/<id>/` on This Mac |
| The API's types | `~/.config/oriel/plugins/oriel.d.ts` and a `tsconfig.json` beside it, which the app writes when they are missing or older than the app |
| Built user plugins | `~/Library/Caches/oriel/plugins/<id>/`, made again when needed |
| Build errors and console output | `~/Library/Logs/Oriel/plugins/<id>.log`, at most 1 MB, the older half cut when full |
| Trust answers | app storage (`UserDefaults`), per plugin id |
| A card's state | in memory while the app runs, and in the instance state file on the card's machine ([Plugin API](/docs/future-work/plugins/api#state)) |

The folder is `~/.config/oriel/plugins/` and not `~/Library/Application
Support/`, because people and agents type the path: it has no space, and
agents know `~/.config`.

## Remote machines

A plugin lives and builds on the Mac. Its page runs in a web view on the
Mac. Only its data comes from the card's machine:
- `oriel.files`, `oriel.git` and `oriel.run` go through the card's `Exec`. On
  a remote machine that is the relay's one SSH session
  ([Running commands](/docs/talking-to-herdr#running-commands)). The page
  cannot pick another machine.
- Paths in the API are the machine's paths. A watch on a remote machine is
  the 2 s check that the default plugins use today
  ([Remote machines](/docs/ui/plugins#remote-machines)).
- Nothing is installed on the machine. One plugin on the Mac works for cards
  on every machine.
- A plugin folder on a remote machine is not loaded. Plugins from a project's
  folder are an [open question](#open-questions).

## Memory budget

Every card that is not on screen costs memory. This budget is built (phase
46, D46). Before it, the app kept the shown tabs' terminals plus the 16 most
recently shown other terminals, and every browser and plugin card it ever
built. Now web cards have a budget too:
- The cards of the shown tab of each window always live.
- The 20 most recently shown other terminals keep their stream and surface
  (16 before).
- The 20 most recently shown other web cards (browser and plugin cards
  together) keep their web view.
- Cards in floating windows and cards with unsaved edits are never dropped.
  They do not count toward the 20.
- Both counts are settings in app storage:
  `spareTerminals` and `spareWebCards`. A test sets them with launch
  arguments (`-spareWebCards 2`).
- Least recently shown goes first, over all windows, as for terminals.

A dropped web card lets go of its web view, so its WebContent process ends.
It keeps:
- a still picture of its last frame at 1x, taken when it stops showing
  (`takeSnapshot` works out of a window too, about 8 ms). Stills are not
  purgeable (macOS took purgeable ones back within seconds): one cap of
  200 MB covers every picture in the app, the least recently taken out
  first. A card with no still shows its loader.
- its native state: the label, the header controls' values, the plugin's
  state and the browser's address and back and forward list.

When it shows again, the app builds a new web view under the still. In this
design the plugin's `main` gets the kept state. Today the still goes when
WebKit drew the page, or after 2 s. A browser card loads its page with its back and forward list. It
loses only what lived in the page: the scroll, form input not sent, a
running script.

### The worst case

Costs measured on an M1 Pro (D46; the plugin benchmark of the web build):
an idle app is about 190 MB. A kept terminal is about 30 MB: its surface
about 6 MB, its last picture 17 MB for a full-window card on Retina, and its
herdr run about 7 MB. A plugin card is about 41 MB (40 cards made 1.8 GB). A
browser card with a heavy site costs more: 120 to 200 MB.

| Kept terminals + web cards | App | Kept terminals | Kept web cards | Shown tab (4 terminals, 4 web cards) | Total |
|---|---|---|---|---|---|
| 16 + 16 | 190 MB | 480 MB | 656 MB | 284 MB | about 1.6 GB |
| 20 + 20 (proposed) | 190 MB | 600 MB | 820 MB | 284 MB | about 1.9 GB |
| 25 + 25 | 190 MB | 750 MB | 1,025 MB | 284 MB | about 2.3 GB |
| before phase 46: 16 terminals, every web card kept | 190 MB | 480 MB | 41 MB × every card shown since launch | 284 MB | no limit |

- Dropped cards add at most 200 MB of stills in all.
- Measured in phase 46 on CI's VM: each kept web card costs about 28 MB (its
  WebKit process), a kept terminal about 7 MB of herdr run plus its surface,
  and neither costs CPU at rest. 40 + 40 worked too: 1.7 GB for all 89
  processes.
- A second window adds its own shown tab. The kept counts are shared by all
  windows.
- 20 is a judgment call, as 16 was: D46 rejected 4 (coming back was slow too
  often) and 32 (memory). 20 keeps about the tabs a user goes back to in one
  task.

### The overview

Since phase 46 every overview tile shows pictures: a terminal's snapshot, a
web card's or a chat's still. With 20 + 20 kept it opened in 205 ms, 327 ms
before ([Overview](/docs/ui/window#overview)).

## A missing plugin

A label can name a plugin that is not on this Mac: one that was removed, or
one from another Mac. Its card shows the plugin id and the argument, with
**Show Placeholder** (the pane's terminal) and **Close Pane**. The app never
changes the label, so the card comes back when the plugin does.

## What stays as built

- The label grammar, the placeholder pane and its one-call create
  ([Labels and instance ids](/docs/future-work/plugins/labels)).
- Opens from a card: in the card with Back and Forward, in a new tab right
  after its own (⌘-click), or to its side (⌥-click)
  ([Opening](/docs/ui/plugins#opening)).
- The scheme, the Content Security Policy and the navigation lock
  ([How the web cards work](/docs/ui/plugins#how-the-web-cards-work)), now
  per plugin.
- Files, saves by hash, watches and git in HerdrKit's `Files` and `Git`.
  They move behind the API instead of the fixed bridge.
- ⌘ keys go to the menu first over a web card (D93).

## Out of scope

- A plugin store or registry: plugins are folders that the user or an agent
  makes.
- Installs from a remote source (a git URL, a download): copy the folder.
- More than one user: Oriel is a single-user app on one Mac.
- Plugins outside panes (a sidebar section, a status item, a pill).
- Plugins on iPhone and iPad ([iPhone and iPad](/docs/future-work/iphone-and-ipad#plugins)).

## Open questions

- One plugin with several pages in one card, as the File Explorer (the tree,
  File, Preview, Markdown) and Git (its home and the diff) are today, with
  Back and Forward. Recommendation: open.
- Network from a plugin page (an allow list of origins in the manifest, as
  Figma does). Recommendation: not now. A plugin with `run` can use `curl`
  on the machine.
- Plugins from a project folder (`<repo>/.oriel/plugins/`), also on a remote
  machine. Recommendation: later.
- Plugin settings drawn by the app from the manifest (as Raycast does).
  Recommendation: later. A plugin keeps what it needs in its state.

## Options

Each major choice, with the options compared. The recommended one is the
design on these pages.

### The plugin format

| Option | Pros | Cons |
|---|---|---|
| One `.ts` file (as pi's small extensions) | the least to write | no place for a header, file patterns or permissions before code runs; no CSS or assets |
| A folder with `manifest.json` and an entry file (Obsidian, Figma) | the app knows the header, patterns and permissions at once; any number of `.ts`, CSS and asset files | two files for the smallest plugin |
| An npm package (`package.json` with an `oriel` field, as VS Code, Raycast) | familiar to web authors; dependencies in one file | a `package.json` even with no dependencies; npm habits (scripts, a build step) that the app does not run |

Recommended: the folder. The manifest must be read before any code, and a
folder holds the code, CSS and assets with no packaging step.

### The memory policy

| Option | Pros | Cons |
|---|---|---|
| One shared count for terminals and web cards (for example 40) | one number | a user with many web cards drops every terminal, and the other way; the two costs differ (30 MB and 41 MB) |
| Two counts, 20 terminals and 20 web cards | each kind keeps its recent cards; the worst case is easy to state | two settings |
| A byte budget | follows real memory | hard to test and to explain; rejected in D46 |

| Option for a dropped web card | Pros | Cons |
|---|---|---|
| Its still picture | the card looks the same at once, as a terminal does; purgeable, so it costs nothing in the worst case | `takeSnapshot` must run while the view is in its window, or it can come back blank |
| Its kind's icon | no snapshot code | a blank card flashes before the page comes back |

Recommended: two counts of 20 and a still, with the kind's icon when there is
no still. Both counts are settings.

### Plugins in the model

| Option | Pros | Cons |
|---|---|---|
| One registry of manifests for every kind the app draws, the browser too | the chooser, ⌘K, Open With and agent listings read one list | the browser's manifest is written in Swift |
| Built-in kinds as a Swift enum, plugins beside them | no change to built code | every list has two sources; the default plugins stay special |

Recommended: one registry. The user asked for one model, and the default
plugins then test the public API.
