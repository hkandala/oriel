## Where each piece of state lives

| State | Example | Where | Seen by |
|---|---|---|---|
| the pane and its place in the layout | — | herdr pane | every device and the herdr TUI |
| plugin, pane kind, instance id | `git-history#k3f9q2` (`/<pane>` only when the plugin has several) | the pane label | every device |
| the argument: what the pane shows | `main`, `docs/DESIGN.md` | the pane label | every device, the TUI border |
| view state | selected commit, filters, scroll anchor; a web card's current address and scroll position | a JSON file on the pane's machine, keyed by iid | every device that reaches the machine, when it builds the card |
| rename signal | `oriel_rev` | a herdr metadata token | every device (`pane.updated`) |
| preferences | diff style | the app, per device | this device |
| plugin code and consent | — | the app | this device |
| in-memory UI state | hover, expanded rows | the page | this card only |

<Callout title="Rule for authors">
If losing it on a reload would annoy the user, put it in
`setArg` (small, defines the pane) or `oriel.state` (bigger). Everything
else stays in the page.

`oriel.state` is only for view state: where the user was looking. Another
device does not see a change until it builds the card again. Data that every
device must see live belongs in files on the machine: read them with `run`,
and read them again when they may have changed (for example on the
`snapshot` event).
</Callout>

## The instance state file

```text
$HOME/.local/state/oriel/<session>/<plugin-id>/<iid>.json
```

`<session>` is the herdr session name.
It is a fixed path (not `XDG_STATE_HOME`), because the Mac and the iPhone
reach the machine through different shells and must agree on one file. The app passes
it relative to the home folder, where every command starts
([herdr on each machine](/docs/talking-to-herdr#herdr-on-each-machine)).
- On the pane's machine: next to the data, shared by Mac and iPhone, kept
  across app reinstalls, no sync service.
- Read with one `cat` when the card is built (a missing file means the
  initial value).
- Written debounced (500 ms), at most 256 KiB, atomically over stdin. Each
  writer uses its own temporary file:
  ```sh
  sh -c 'umask 077; mkdir -p "${1%/*}" && cat >"$1.$$" && mv "$1.$$" "$1"' sh <path>
  ```
  Last writer wins.
- The app also writes `<plugin-id>/_plugin.json` (title, source, version) each
  time it creates a pane of that plugin, so a device without the plugin can
  suggest installing it.
- **Cleanup:** the device that closes a web or plugin pane removes its state
  file (`rm -f`). On connect, the app runs once
  `find .local/state/oriel/<session> -type f -mtime +30 -delete`, so files of
  panes closed elsewhere (in the TUI, by a script) go after 30 days. Every
  write refreshes a file's age; a card nobody touched for 30 days starts
  fresh.

## Restore on a fresh app start (any device)

<Flow steps={[['1 · snapshot', 'connect each machine'], ['2 · classify', 'oriel: · agent · terminal'], ['3 · resolve', 'core, then linked, then installed; missing → placeholder card'], ['4 · key the card', '(machine, terminal_id)'], ['5 · render', 'web page + pane context + state file']]} />

1. Connect each machine and read `session.snapshot`.
2. Classify every pane by its label:
   - matching the `oriel:` grammar → (plugin, pane, iid, arg); for `web`, the
     argument is the typed URL ([Web page](/docs/plugins/web-page) load rules
     apply);
   - otherwise → `agent` if herdr set `pane.agent`, else `terminal`.
3. Resolve the plugin in the registry (core, then a linked folder, then an
   installed plugin):
   - missing → a card with the plugin id and argument, **Show placeholder**
     (switch the card to the pane's terminal) and **Close pane**. On macOS,
     if the machine has `_plugin.json` with an `https` source, the card also
     shows **Install from ‹source›…**, marked "Suggested by ‹machine›" and
     always through the consent sheet. The label is never changed, so the
     pane comes back once the plugin is installed;
   - unknown pane name, an `api` too new, or a required preference unset →
     the matching message or the "Set up" view.
4. Key the card `(machine, terminal_id)`, like every card
   ([Reconcile](/docs/talking-to-herdr#reconcile)). A card that is already
   alive stays as it is.
5. When the card is first shown: build its web page, inject the pane context, read
   the state file if the plugin uses one, render.
6. On every later snapshot: a changed argument re-renders; a pane that is
   gone destroys the card.

Nothing in these steps reads app storage except plugin code, consent and
preferences.

## When a card reads its state

A card reads its state file only when it is built (D59):
- a fresh app start or a new device;
- the card shown again after it was closed or evicted
  ([Plugin UI](/docs/plugins/plugin-ui#how-it-works)), or its plugin reloaded;
- on iOS, a card the system discarded while the app was in the background.
  Returning from the background is not a fresh start: cards still in memory
  keep their state.

While a card is open, it never reads its state file again by itself, so
another device's writes do not move it. Every plugin card and web card has
**Refresh** in its header: it writes this card's pending state, then
rebuilds the card as if it were opened again, so it loads the page and its
state from the machine.
