## What a machine is

- A **machine** is a host: a computer that runs herdr (D43). This Mac now,
  SSH hosts later. Each machine has its own icon, because the title row's
  machine button shows only the icon ([Machine button](/docs/ui/window#machine-button)).
- A machine runs several herdr **sessions** (`default`, `pi-herd`, …), each
  one herdr server. The sessions of one machine share one SSH connection
  (ControlMaster) and nothing else: each session has its own events, streams
  and state folder.
- A window shows one machine. Sessions open as pages: its sidebar has one
  page per session the user opened in that window
  ([Sidebar](/docs/ui/window#sidebar)). A new window opens one page, the
  `default` session.

## The machine list

- **The app keeps its own list of remote machines**, on macOS and iOS alike
  (D54): name, SSH target, icon and id, in `UserDefaults`. One code path on
  both platforms. Remote machines come after This Mac.
  - The list is JSON under the `machines` key. A run launched with
    `-session` (the e2e tests, a run against a throwaway session) never reads
    or writes it: it takes `-machines <json>` or no machines, so a test never
    reaches the user's hosts.
  - A window remembers its machine's id; `-machine <id>` picks it at launch.
- **This Mac** is always in the list, with a laptop icon when the Mac has an
  internal battery, else a desktop icon.
- **A machine's sessions** come from `herdr session list --json`, run on that
  machine. The Open Session panel lists them
  ([Open Session](/docs/ui/window#open-session)). herdr on the Mac is needed
  only for This Mac's sessions, not for remote machines.
- **herdr's machines (macOS):** when herdr is on the Mac, the Add Remote Host
  sheet lists the targets of the enabled entries of `herdr machine list --json`
  (`{id, label, target, session, enabled}`) that are not in the app's list,
  each with a checkbox. While the app's list is empty, they start checked.
  The app never writes herdr's list.

## macOS
- **SSH is the system `ssh`.** The user's `~/.ssh/config`, agent, keys,
  `ProxyJump`, YubiKey and Tailscale SSH work unchanged.
- **One ControlMaster per host,** started on purpose, once, by the first run
  that finds none (`SSHExec` in HerdrKit):
  ```sh
  ssh -M -N -f -o ControlPersist=10m -o ServerAliveInterval=5 \
      -o ServerAliveCountMax=3 -o ConnectTimeout=10 \
      -o ForwardAgent=no -o ForwardX11=no -o ClearAllForwardings=yes \
      -o LogLevel=ERROR -o BatchMode=yes -S ~/Library/Caches/oriel/<h8> <target>
  ssh -F /dev/null -S ~/Library/Caches/oriel/<h8> -O check <target>   # its pid
  ```
  - With `-f`, ssh goes to the background once it is authenticated and the
    socket serves, so the start's exit status says whether it worked. Its
    stderr (merged into stdout) is ssh's reason when it did not.
  - `LogLevel=ERROR`: that reason is ssh's own error lines only. The server's
    login banner and ssh's notices ("Permanently added … to the list of known
    hosts") are INFO, so they never show on the Disconnected page.
  - Later runs use `-F /dev/null -o ControlMaster=no -o BatchMode=yes
    -o ProxyCommand=/usr/bin/false -S ~/Library/Caches/oriel/<h8>`. Without a
    master they fail at once instead of opening their own connection and
    prompting again. They send none of the user's configured forwards to the
    master. With a master, ssh never reads the target's config, so an alias
    works with `-F /dev/null` (checked on OpenSSH 10.3).
  - Before each run the app checks that the master lives with `kill(pid, 0)`,
    not a process: the pid comes from `-O check` once per start. A master that
    is gone (killed, or ended by its keepalive) is started again by the next
    run. Its socket stays behind when it was killed, and a new master does not
    bind over it, so the app removes it first. A master that outlived an app
    that crashed is not used: it may still hold that app's sessions. It ends
    10 min after its last one.
  - Starting the master first means one password, OTP or key prompt per host.
    With `ControlMaster=auto`, parallel first calls each prompt. Starts are
    one at a time per host; runs that need a master wait for the start in
    flight.
  - `<h8>` is 8 hex characters of a hash of the SSH target. The folder is per
    user, mode 0700, with no spaces. The path stays under the 104-byte socket
    limit for user names up to 50 characters, with ssh's 17-character
    temporary suffix.
  - Forwarding is off, so a machine cannot reach the Mac's SSH agent or ports
    through the app's long-lived connection. The app's own `-O forward` calls
    still work.
  - **A dead link:** ssh's own keepalive (`ServerAliveInterval=5`,
    `ServerAliveCountMax=3`) ends the master within about 15 s after the
    network goes (a network change, sleep, a server restart). The next run
    starts a new one. The app runs no `-O exit` of its own on a failed check.
  - On quit the app runs `ssh -S <ctl> -O exit <target>` for each master.
- **The relay:** every run of a remote machine (calls, the events stream,
  every terminal stream) goes through one SSH session. A server may allow
  only a few sessions per connection (`MaxSessions`; a server with one-time passcodes refused
  the third), and a second connection would ask for a second passcode. The
  first run on a new master starts that session; it runs a Perl script
  (`Relay.script` in HerdrKit, sent in the envelope; nothing is installed).
  It spawns each run as `sh -c <command>` and carries every run's stdin,
  stdout, exit status and stderr over its own stdin and stdout, as lines:
  - the app sends `o <id> <command hex>`, `w <id> <line>`, `c <id>` (close
    stdin) and `k <id>` (close stdin, then SIGKILL by pid);
  - each run's writes wait in its own buffer, so a run that reads nothing
    never holds up the others; its `sh` runs the command with `exec`;
  - the relay sends `l <id> <line>`, and `x <id> <status> <stderr hex>` once a
    run's output ended and it was reaped.
  - herdr's bridge, events and terminal streams are all lines, so this needs
    no other framing; one process writes them, so lines of two runs never mix.
  - When its stdin ends (the app quit, the connection dropped) it exits, and
    every run's stdin closes with it, so every run ends as before.
  - Perl is on nearly every Unix (Debian's `perl-base` is essential, macOS has
    it). The relay greets with `oriel-relay 1` within 10 s; a machine where it
    does not shows "Oriel needs Perl on ‹machine›", and the next run tries
    again.
  - herdr's own transports do not fit: `herdr --remote` runs one
    `remote-client-bridge` session, but it speaks herdr's internal binary
    client protocol; `herdr --machine` opens one session per request, as
    `remote-api-bridge` does.
- **Automatic starts never prompt.** Every start a run makes uses
  `BatchMode=yes`. How it fails decides what follows:
  - ssh needs an answer (its text has "Permission denied", "Host key
    verification failed", "passphrase" or "IDENTIFICATION HAS CHANGED"): the
    machine is blocked. Runs fail at once with ssh's text and start no ssh,
    and the pages show **Disconnected** with **Connect**
    ([States](/docs/ui/states)).
  - Anything else (no network, the host down, a refused connection): runs fail
    at once until the next try, 2, 4, 8, 16, then every 30 s, and the pages
    show Reconnecting.
- **Prompts:** only **Connect** and Add Remote Host start a master that may
  ask. That start sets `SSH_ASKPASS` to a small script the app writes beside
  the sockets (mode 0700) and `SSH_ASKPASS_REQUIRE=force`. ssh runs the
  script with ssh's own stdin and stderr, which are the app's pipes: the
  script prints the question, base64 on one line after a marker, to stderr
  and reads the answer from stdin. The app shows the question in a dialog of
  the window that connects ([Add a machine](/docs/ui/add-a-machine)) and
  writes the answer to ssh's stdin. Nothing is stored. A key or agent that
  works needs no question, so the start asks only what ssh asks.
  - A new host key shows ssh's text with its fingerprint and asks yes or no;
    **Connect** answers yes, and ssh writes `known_hosts` itself.
  - Every answer is hidden: a password, a passphrase, a one-time passcode or
    any other code. Only the host key question has no field.
  - Cancel ends the start; the page stays Disconnected.
  - A `none` question (a security key's touch) gets no dialog.
  - Why not the `osascript` dialog the design had: the app's dialog belongs to
    the window that asked, follows the app's look, and an e2e test can answer
    it.
- **herdr on the machine:** the remote login shell gives its path, one run
  over the master, `"$SHELL" -lic 'echo <marker>; command -v herdr'`, once per
  master; a missing herdr is asked again at most every 30 s. The page then
  shows "herdr is not installed on ‹machine›" with the install command.
- **New tabs and workspaces** pass `cwd` `~`, which herdr reads as the
  machine's home, so the app never sends This Mac's home to a remote machine.
- **What the prototype leaves for later:** Local Network privacy (below),
  herdr's machine list in the sheet, rename, reorder and remove of a machine,
  ⌥-click on a remote machine (it switches the window, not a new one), a
  remote home shown as `~` in card headers, `dial`, and file drops and image
  paste to a remote machine.
- **Local Network privacy (macOS 15+):** an `ssh` started by the app counts as
  the app. The app declares `NSLocalNetworkUsageDescription`, resolves the
  target with `ssh -G`, and opens an `NWConnection` to a LAN address before
  the first SSH, so the system asks once. Tailscale addresses are not
  affected.

## iOS

- One Citadel SSH connection per host, with exec channels on it.
- The key is a Secure Enclave P-256 key (`ecdsa-sha2-nistp256`). It cannot
  leave the device. The add-machine sheet shows its public line to copy into
  `authorized_keys`.
- The first connect shows the host key's SHA256 fingerprint and asks. After
  that the key is pinned, and a changed key blocks the connection.
- The phone reaches the Mac like any SSH machine: turn on System Settings ›
  General › Sharing › Remote Login, then add the Mac by its Tailscale or LAN
  name.
- Reachability is the user's network (LAN or Tailscale). There is no relay.
  Jump hosts come later (Citadel has `jump(to:)`).
- Citadel has no keepalive; the [health check](#health-check) finds dead
  links.
- When the app goes to the background, it closes its terminal streams. iOS
  then gives about 30 s. The app holds its other connections with
  `beginBackgroundTask`, closes them when that time ends, and reconnects and
  reads the snapshot again on return.
- [Spike S7](/docs/build-order#s7-ios-transport) tests Citadel's exec
  channels before the iOS work starts.

## Open sessions

- A session is open while it has a page in at least one window. Each open
  session has one `HostStore`, shared by every window that shows it
  ([Architecture](/docs/architecture#pieces)). The app keeps one registry of
  them, by session name; a page takes its session's store from it, made on
  first use. Detach Session disconnects the store.
- An open session keeps its control plane open (one event stream plus short
  calls), so notifications, the Dock and pills cover every open session in
  every window. The Agents button covers the page in view.
- A session with no page has no store, no snapshot reads and no event stream.
  A machine with many sessions costs nothing until the user opens them.
- Terminals stream only for the tabs shown in a window
  ([What streams](/docs/talking-to-herdr#what-streams)).

## Health check

One loop per open session checks that it answers.
- The check is `session.snapshot`, the read the app needs anyway. It carries
  herdr's version and catches any event the app missed.
- It runs every 30 s while the session is healthy. A failed read switches it
  to every 2 s, so a session started again comes back at once.
- A session counts as live only while the check answers. While it fails, its
  cards gray out.
- On a remote machine a failed check runs over a new connection when the old
  one is gone: on macOS the next run starts a new ControlMaster (ssh's
  keepalive ends a dead one, [macOS](#macos)); on iOS a new Citadel
  connection.
- **Automatic retries never prompt.** On macOS they run with
  `BatchMode=yes`. A host that needs a password, an OTP or a key prompt shows
  **Disconnected** with **Connect** and stops retrying; only that button may
  prompt.
- When a check succeeds after a failure, the app opens the event stream and
  the terminal streams again: the same path as the first connect
  ([Checks on connect](#checks-on-connect)).

## SSH sessions

- A remote machine uses one SSH session, the relay's
  ([macOS](#macos)), whatever it streams. This Mac uses no SSH.
- Port forwards for web pages use no session: `MaxSessions` counts only
  sessions.

## Checks on connect

1. `session.snapshot`. Its errors say what is wrong: herdr missing (the
   install command), herdr too old, or the server not running
   ([herdr on each machine](/docs/talking-to-herdr#herdr-on-each-machine)). If
   the server is not running:
   - **This Mac:** a **Start** button. A new window's first page starts its
     session this way when it is stopped. In the Open Session panel, a stopped
     session or a new name starts the same way. A server the app started gets
     its first workspace in `$HOME`; a server that already runs is left
     alone. The app starts the
     server as a one-shot launchd job (D47). launchd, not the app, is the
     server's parent and "responsible process": macOS privacy prompts never
     name Oriel, the server has its own process group, and it outlives the app.
     - `launchctl bootstrap gui/<uid>` (the user's GUI domain) loads the job
       `dev.hkandala.oriel.herdr.<S>`, which runs
       `<herdr path> --session <S> server` (the path from the login shell).
     - `RunAtLoad` without `KeepAlive`: once `herdr session stop` ends the
       server, launchd never runs it again (`launchctl submit` restarted it).
     - `ProcessType Interactive`: launchd's default throttles the CPU and I/O
       of the server and every agent in it.
     - stderr goes to `~/Library/Logs/Oriel/<S>.log`.
     - The job gets the user's environment keys from the login shell (`PATH`,
       `HOME`, `SSH_AUTH_SOCK`, `XDG_*`;
       [herdr on each machine](/docs/talking-to-herdr#herdr-on-each-machine),
       D47), so the server and the CLI agree on paths.
     - An older job of the label is booted out first (a label loads only
       once). A running server, one that answers a snapshot, is never booted
       out: the app uses it.
   - **A remote machine:** the same **Start** button runs
     `sh -c 'nohup <herdr path> --session S server </dev/null >/dev/null 2>&1 &'`
     over SSH and polls `session.snapshot` as This Mac's start does. A new
     window on a remote machine opens its `default` session without starting
     it.
2. Open the event stream. Its `subscription_started` reply counts as an
   event, so the app reads the snapshot once more and misses nothing between
   the two steps.

The agent picker reads `integration.list` when it opens
([Agent](/docs/plugins/terminal-and-agent#agent)).
