## What herdr returns

Each herdr tab is a split tree. Every split has a direction (`right` or
`down`) and a ratio. herdr stores the tree across restarts.
`session.snapshot.layouts[]` gives each tab's layout as a flat list:

```json
{"tab_id":"w1:t1","area":{"width":120,"height":40},
 "panes":[{"pane_id":"w1:p1","rect":{…}},
          {"pane_id":"w1:p3","rect":{…}},
          {"pane_id":"w1:p2","rect":{…}}],
 "splits":[{"id":"split_0_root","direction":"right","ratio":0.55},
           {"id":"split_1_1","direction":"down","ratio":0.5}]}
```

- A split's `id` is `split_<n>_<path>`, as herdr writes it:
  - `<n>` is the split's place in `splits[]`, counted from 0. The list is
    depth-first, with a parent before its children.
  - `<path>` is `root` for the root split. For every other split it has one
    digit per step from the root: `0` = first child, `1` = second child.
  - Example: `split_1_1` is the second split in the list, and it is the root's
    second child. A split under its first child would be `split_2_10`.
- `panes[]` is in depth-first order, first child before second.
- For `layout.set_split_ratio`, `path` is `<path>` as booleans (`0` → `false`,
  `1` → `true`). The root is `[]`.

## Rebuilding the tree

```text
build(path) = split at path exists ? Split(dir, ratio, build(path+0), build(path+1))
                                   : Leaf(next pane from panes[])
```

- About 15 lines. If the leaf count does not equal `panes.count`, the app
  falls back to `layout.export {tab_id}` (the same tree, nested). The order is
  depth-first in herdr's source but not a documented contract, hence the
  check.

## Drawing and resizing

<SplitDemo />

- A tab page is the size of the strip. Each split divides its rectangle by the
  ratio, with a fixed 8 pt gap between cards. The gap is the divider. herdr's
  cell rectangles are not used for drawing.
- Each terminal card tells herdr its own size in cells, so the PTY fits the
  card.
- Resizing works on the split tree only. To put a pane elsewhere, move it.

## Dividers

- **Hit area.** Each split's 8 pt gap is its divider, with a 16 pt hit area
  centered on it and the column or row resize pointer. On hover, and while it
  is dragged, a grip shows: a 36 × 3 pt capsule (3 × 36 pt for a side-by-side
  split) in the secondary color at 0.6 opacity (gorex's muted icon color). It
  fades in over 0.2 s.
- **Drag.** The split moves in the view at once. The app holds its own ratio
  for that split until herdr's snapshot shows a new ratio, herdr refuses the
  write, or herdr already has that ratio. On release the app sends
  `layout.set_split_ratio {tab_id, path, ratio}`, with the ratio kept in
  0.1–0.9. Terminals keep their grid until the drag rests for 150 ms, so a
  drag does not flood herdr with PTY resizes or reflow at every step.
- **Double-click** a divider: ratio 0.5.
- **Equal splits.** herdr halves the pane it splits (50 / 25 / 25). After
  every split the app makes (the header buttons, the menus, ⌘D, ⇧⌘D), the app
  reads a fresh snapshot and evens out the run of same-direction splits that
  holds the new pane, so three panes in a row get a third each, as in Rex:
  - A child split in the other direction counts as one unit.
  - Each split gets "units on its first side ÷ units under it".
  - One `layout.set_split_ratio` per split whose ratio changes, then the app
    reads the snapshot.
  - Closing a pane does not rebalance.
- **Balance** (⌃⌘=, View ▸ Pane ▸ Balance Splits) applies the same rule to
  every split of the selected tab; an even tab sends nothing.
- **Keys.** ⌃⌘ and an arrow sends
  `pane.resize {pane_id, direction, amount: 0.05}` for the keyboard card.
  herdr moves the nearest divider that way: right and down raise its ratio,
  left and up lower it. With no divider that way, herdr returns
  `changed:false`.
- **Accessibility.** Each divider is an adjustable element, "Divider between
  ‹a› and ‹b›", where ‹a› and ‹b› are the first pane title of each side. Its
  value is the ratio as a percent. Increment and decrement move it 5 % and
  send the ratio. Its identifier is `divider.<tab id>.<path>`, with the path
  as `0` and `1` digits, or `root` for the root split.

## The keyboard card

Every card is drawn at full strength, in a key window and in one that is not
(D64). The keyboard card takes the keyboard-card fill and stroke, the others
the plain card fill, from the look's tokens
([Theme and accessibility](/docs/ui/theme-and-accessibility#appearance-and-interface-style)).
In Glass the two are close: the keyboard card is only a little brighter.

- A window that watches the session dims every card's header and terminal
  content (its host view, not an overlay, so card edges stay crisp) to 0.85
  (D66).
- The card's accessibility value says the dim: "content 100%" or "content 85%".

## Layout motion

- When the tree changes (a split, a close, a move, a ratio from herdr), card
  frames animate over 0.2 s, ease-out.
- During the motion each terminal keeps its size, clipped by its card, and
  resizes once 150 ms after it ends, as for any change of the card's size
  ([Size](/docs/talking-to-herdr#size)): resized at every frame, a terminal
  went blank for most of the motion.
- A divider drag follows the pointer with no animation.
- Reduce Motion: no animation.

## Moving the keyboard

The keyboard card is the app's own (see below). Keys move it, and never call
herdr's focus methods (D13):
- ⌥⌘ and an arrow (View ▸ Pane ▸ Select Pane Left, Right, Up, Down): the
  keyboard goes to the card that herdr's read-only
  `pane.neighbor {pane_id, direction}` names. One call per key, so the app
  has no geometry code of its own for this.
- ⌘[ and ⌘] (Select Previous Pane, Select Next Pane): the previous and next
  card in the tree's order, round the ends.
- Moving the keyboard to a card that a zoom hides restores the zoom.
- ⌥⇧⌘ and an arrow (Move Pane): swaps the keyboard card with its neighbor
  that way, with `pane.swap {pane_id, direction, focus:false}`. The keyboard
  stays with the pane.
- After a move to a new tab, another tab or a new workspace, the window
  selects the tab the pane went to, and the pane keeps the keyboard. A pane
  moved to another workspace gets a new pane id; its terminal and card stay.
- **Focus follows mouse** (View ▸ Pane ▸ Focus Follows Mouse, off by
  default): a card gets the keyboard when the pointer rests on it for
  0.15 s. Only in the key window, never while a mouse button is down, and
  never while the user types in a text field (the palette, a rename, a
  filter). While the pointer rests, the app checks again every 0.15 s, so a
  rename or a drag that ends under the pointer still counts; it moves the
  keyboard once. Never while a menu is open, and only for cards of the
  selected tab.

## Zoom is the app's own

- One zoomed card per page in each window, in memory.
- It is drawn by the split tree itself: each split above the zoomed card
  stacks its two sides, the zoomed side at the full size and the other hidden
  at the size it has without zoom. The same views stay in place, so no
  terminal view moves between hosts and no other PTY resizes. (Drawing the
  zoomed card in a layer of its own moved its terminal view to a new host,
  and SwiftUI did not give it back on restore.)
- herdr's `pane.zoom` is not used. It moves herdr's focus, marks the whole tab
  seen, and makes herdr refuse moves into or out of that tab.
- If a herdr TUI user zoomed a tab, the app ignores that flag and draws the
  full layout. A move into that tab returns `zoomed_tab`, which the app shows.

## PTY size has one owner

- One window controls each session (D66), so the PTY of a pane follows the
  card size in that window. A window that watches the session opens
  `observe`, which clips or pads to its own card size
  ([Control between windows](/docs/talking-to-herdr#control-between-windows)).
- While our `control` stream is attached, herdr locks that PTY to our size
  and ignores herdr TUI layout resizes. After release the PTY keeps our size
  until a herdr TUI lays the tab out again.
- herdr's layout rectangles never show the PTY size. A `control` frame's
  `width` and `height` do.

## Selection and "seen" are the app's own

- Each window has its own machine, open pages, page in view, sidebar view
  and sidebar width ([Data](/docs/data#every-piece-of-data)).
- Selection is per page. Each page of a window keeps its selected workspace,
  the selected tab of each workspace, the keyboard card of each tab, its
  zoomed card, and a tab it just made (selected once a snapshot shows it).
  The window's page holds them in memory, not the session's `HostStore`, so
  two windows on one session select on their own. Switching pages brings the
  selection back.
- A tab that is gone falls back to herdr's active tab of that workspace, else
  its first tab. A workspace that is gone falls back to herdr's focused
  workspace, else the first one.
- One `PaneViewRegistry` per window holds the terminals of all its pages.
  Only the shown tab of the page in view streams; the cache keeps about 24
  streams over all pages of all windows (D46,
  [What streams](/docs/talking-to-herdr#what-streams)).
- Control is per session, across windows (D66): the window where the user
  last typed or clicked in a terminal controls that session's panes. It is
  not part of a window's selection.
- The card with the keyboard is the app's own too, one per tab in each
  window: coming back to a tab gives the keyboard to the card the user last
  used there. herdr's
  focused pane only picks it the first time a tab is shown, the same kind of
  fallback, and the app never tells herdr.
- **The app never calls herdr's focus methods** (`pane.focus`, `tab.focus`,
  `workspace.focus`, `agent.focus`). Each of them moves every attached herdr
  TUI to that tab and marks the tab seen (herdr source, and seen in our
  tests). A herdr TUI may be open next to the app, and it must not jump.
- So the app tracks "seen" itself, in memory, per agent, from
  `completion_seq`:
  - herdr gives every agent status change a number from one counter per
    server. When an agent finishes (working or blocked → idle),
    `completion_seq` is the number of that change. At the agent's next status
    change, for example when it starts working again, herdr sets it back to
    null. So an unseen finish clears when the agent starts working again,
    and the agent then shows the working dots.
  - "Finished, not seen" is "not null and different from the seen value",
    not "greater than": the counter restarts at 0 when herdr restarts.
  - herdr's own `done` status is not used, because herdr goes straight to
    `idle` when a herdr TUI is already looking at that tab.
  - The first time the app sees an agent, it records the agent's current
    `completion_seq` as seen, so old finishes do not flood the Agents
    view or the notifications.
  - Looking at the agent's pane records the current value: its tab is
    selected on the page in view and the window is key.
  - The first snapshot after launch, or after a page opens, reports no
    changes. After a reconnect, changes count.
  - Each device keeps its own seen values, in memory in the session's
    store, shared by its windows. Seeing an
    agent on one device does not clear it on another.
  - Simpler choice: finishes that happen while the app is closed are not
    shown. Revisit when users ask for a list of finishes they missed.
