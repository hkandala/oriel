Chat view for Oriel

Research and mock-ups for one chat interface over Claude Code, Codex, pi and opencode running as TUIs in herdr panes, on this Mac or over SSH. Spiked on Claude Code 2.1.310, Codex 0.163, pi 1.4.0, opencode 1.19.4 (npm) and 2.2.0-dev (source), herdr 0.9.5. October 2026.

TL;DR

  • Two levels work for every agent. Base: any running pane, nothing installed. Read the transcript the agent writes anyway, send with agent.prompt, answer prompts with keys. Side channel: a live connection beside the TUI that gives per-token text and real Approve/Deny buttons. The TUI keeps running in both.
  • Every agent has a side channel, but three of the four need it chosen at launch. Claude Code: hooks and a statusline from --settings. Codex: the TUI started as codex --remote against an app-server Oriel runs. opencode 1.x: --port (2.x always has a local service). pi is the exception: a one-file extension attaches to a running TUI with /reload.
  • In-chat approvals work for all four on the side channel, and the TUI keeps its own dialog open at the same time; the first answer wins (Claude: PermissionRequest hook; Codex: requestApproval fan-out; pi: bridge races the dialog; opencode: /permission/:id/reply). On Base, the chat shows a Needs you drawer with the live terminal and key buttons, and it goes back to chat when the agent stops being blocked.
  • Model and mode: mode toggles are one key on all four (shift+tab or tab). A model change is direct only for pi (/model <exact id>) and side channels (Codex turn/start{model}, pi setModel, opencode 2.x API). Otherwise the chat opens the agent's own picker in the drawer. Never type /model <name> into Claude Code: it writes the user's global settings.
  • The big trap: pickers and extension dialogs leave herdr at idle, so agent.prompt can type into them (proven on pi, Claude Code and opencode). Send must check the screen first.
  • First slice: Base for all four (opencode by polling its SQLite), design A in the card, the Needs-you drawer, read-only model and mode with a one-key mode toggle. Next: the pi bridge, then opencode's server, then launch-time side channels for Claude Code and Codex.

What each agent offers

The two levels per agent. Evidence and samples from throwaway runs are in the four helper reports (sources).

Claude Code

Base. agent_session id → ~/.claude/projects/<cwd slug>/<id>.jsonl, one line per finished block. No live text anywhere on disk. Dialogs report blocked; keys: Return = first option, Esc = no (and ends the turn), arrows for questions and plans.

Side channel (Oriel launches it with inline --settings): a statusLine command streams model, cost, context %, session id and transcript path; a PermissionRequest hook waits on a decision file and answers tools and AskUserQuestion; a PreToolUse hook on ExitPlanMode approves plans. Files only, so it works over SSH.

Company PermissionRequest hooks return allow and beat a deny. The statusline has no mode; read it from the footer.

Codex

Base. The rollout file the pane's codex process holds open (lsof; keep session_meta.source=="cli", newest), parsed from event_msg/item_completed. Approvals never reach the rollout. Keys: y yes, Esc no (and aborts the turn), digits for questions.

Side channel (Oriel starts codex app-server --listen unix://S in a hidden pane and the TUI as codex --remote unix://S): a second client resumes the live thread, gets per-token deltas, gets and answers approvals and questions (the TUI clears), and can start, steer and interrupt turns and change model and effort. The socket speaks WebSocket, so remote needs a small shim.

A plain codex TUI listens on nothing and cannot be joined. No cost figure, tokens only.

pi

Base. agent_session gives the path. A JSONL tree; walk parentId from the last entry. Thinking text, cost per message. No built-in permission prompts; extension dialogs and pickers report idle, so agent.prompt answered a confirm in the spike.

Side channel: a ~200-line extension (-e at launch, or the extensions folder plus /reload on a running TUI) with a unix socket: live deltas, send with steer or follow-up, images, abort, set model and thinking, every extension's select/confirm/input raced with the TUI, and herdr:blocked so herdr refuses prompts while one is open.

Built-in slash commands still need keys. pi --mode rpc on the same file splits the tree: never.

opencode

Base (1.x, the npm release). No transcript file: SQLite (opencode.db, part rows written per block), found by lsof, session id from herdr's TUI plugin. Poll it with sqlite3 or opencode db. Dialogs report blocked; keys: Return allow once, Esc reject, ←/→, digits for questions; interrupt is Esc twice.

Side channel: 1.x with --port (or serve + attach), and every 2.x TUI (a local service in service.json). SSE over curl -N is plain lines, so it rides Oriel's relay: live deltas, permissions, questions, todos; replies, prompt_async, abort, agent and model changes.

2.x changes the API and storage. Model and variant pickers report idle.

One adapter interface

One chat view, one model of a conversation, one small adapter per agent. An adapter turns its sources (transcript lines, SQLite rows, hook files, SSE, a bridge socket, app-server events) into ChatEvents, and turns ChatActions into herdr calls, keys or side-channel calls. herdr's agent_status and the screen (pane.read) are shared by all adapters, not per agent.

// Events in: what the view draws. Ids are the agent's own (tool call id, message id, request id).
enum ChatEvent {
    case session(id: String, cwd: String)                         // new id on /clear, /new, /fork: restart the source
    case user(id: String, text: String, images: [Image], queued: Bool)
    case text(id: String, markdown: String, final: Bool)        // final:false = a live delta (side channel only)
    case thinking(id: String, text: String?, seconds: Double?)   // Claude and Codex: no text
    case tool(ToolCall)                                     // sent again as it runs and ends
    case subagent(id: String, parentTool: String?, name: String, status: Status)
    case plan([PlanItem])                                    // todos, Codex plans, opencode todo.updated
    case ask(Ask)                                           // structured request: only from a side channel
    case askEnded(id: String, answer: String, by: AnsweredBy)     // .chat, .terminal, .policy (another hook decided)
    case turnEnded(status: Status, seconds: Double?)             // done, interrupted, error(text)
    case settings(Settings)                                   // model, effort or thinking, mode, context %, cost
    case notice(String)                                       // compaction, model switched by the agent, retry
}
struct ToolCall { let id, name, target: String; var params: [String: String]; var state: Status; var summary: String?; var diff, output: String? }
struct Ask { let id: String; let kind: Kind /* tool, question, plan */; let title: String; let detail: String? /* command, diff, plan */
              let options: [Option] /* label + role: allow, allowAlways, deny, choice */; let allowsText: Bool }

// Actions out: what the composer, the cards and the menus ask for.
enum ChatAction {
    case send(text: String, images: [URL])    // agent.prompt (Base) or the side channel
    case interrupt                            // Esc (opencode: Esc Esc) or the side channel
    case answer(ask: String, option: String, text: String?)
    case keys([String])                       // the Needs-you drawer, behind the key guard
    case setMode(String), setModel(String, effort: String?)
    case command(String)                      // a direct slash command, typed
}

// One per agent: ClaudeChat, CodexChat, PiChat, OpencodeChat. The screen-text chat stays for every other pane.
protocol ChatAdapter {
    func events(pane: Pane, machine: Machine) -> AsyncStream<ChatEvent>
    func perform(_ action: ChatAction, pane: Pane, machine: Machine) async throws
    var can: Capabilities { get }              // what to draw: live text, in-chat asks, model menu, mode values
}

Shared, not per agent

  • State from agent_status: the Working row, Needs you, Done.
  • The Needs-you drawer: pane.read {source:"visible"} and key buttons.
  • The send guard: no agent.prompt while the screen shows a picker.
  • Grouping tool calls between two replies, summaries ("Read 3 files, ran 1 command").
  • The tail and poll runners over the relay.

Per agent (Base)

  • A finder: herdr's agent_session, lsof, the path rule.
  • A lenient line parser, skipping unknown types.
  • A key map: interrupt, mode toggle, and the answer keys of its known dialogs.
  • The list of slash commands that open pickers.

Per agent (side channel)

  • Claude: hook and statusline scripts in inline --settings; request and decision files.
  • Codex: a JSON-RPC client over the app-server socket.
  • pi: the bridge extension and its JSONL socket.
  • opencode: SSE plus a few curl calls.

Approvals, questions and blocked states

Two ways to answer, picked per request. The TUI never closes and always keeps its own dialog, so the user can answer in either place.

WayWhenWhat the chat showsHow the answer goes
1. In-chat carda side channel sent a structured Ask an approval card in the stream (pinned above the composer while scrolled away) with the command, diff or plan, the agent's options as buttons, and a text field for "tell it what to do instead" Claude: decision file read by the waiting hook. Codex: the JSON-RPC reply. pi: the bridge's answer. opencode: POST …/reply. The TUI dialog closes by itself; if the user answers in the TUI first, the card shows "Answered in terminal"
2. Needs-you drawerBase: agent_status is blocked, or a picker the chat opened is up a drawer over the composer with the live bottom of the terminal and the agent's answer keys as named buttons, plus Open Terminal (design D) a fixed key map per agent, no screen parsing: Claude Code Return = first option, ↓, Esc = no and stop; Codex y, digits, Esc; opencode Return, ←/→, digits, Esc; pi ↑/↓, Return, Esc. Each key is sent only if the screen has not changed since it was read (the key guard). The drawer closes and the chat returns when the agent works or idles again
Esc is not a plain "No". In Claude Code and Codex it rejects and ends the turn. On the side channel, deny with a message instead (Claude {"behavior":"deny","message":…}, Codex decline), so the agent can go on. On Base, label the button "No, stop".

Things to get right

  • Policy wins. On this Mac, company PermissionRequest hooks return allow and beat Oriel's deny. Read the result (permissionDecision.source, the tool result) and show "Allowed by policy" instead of pretending the deny worked.
  • Races. A Claude hook keeps waiting after a TUI answer: give each request an id, and end the hook when the tool's result appears. PermissionRequest has no tool_use_id; pair it with the PreToolUse before it.
  • Few prompts in practice. This user's aliases start Claude Code with --dangerously-skip-permissions and Codex with --yolo, and managed configs auto-review most commands. Approvals matter, but questions (AskUserQuestion, request_user_input, opencode questions) and plan approval come up as often.
  • Picker trap. Pickers report idle. Before each send, read the last screen lines and refuse with "A menu is open" plus Open Terminal if they look like a picker (each agent's picker footer is a fixed string: "Enter to select", "↑↓ navigate", "⇆ select").

What the first slice ships

  1. Base for all four. Finders and lenient parsers: pi (path), Claude Code (id → path), Codex (lsof, filtered), opencode (opencode db or sqlite3 polled once a second while shown). Local and remote.
  2. Design A in the card, behind the chat|term switch: user boxes, replies, tool groups collapsed to a summary line, thinking rows, subagent and plan rows, the Working row from agent_status.
  3. Composer: agent.prompt with its refusals and the picker guard; Stop sends the agent's interrupt keys.
  4. Needs you: the drawer with each agent's named answer keys and the key guard.
  5. Pills: model, mode, context, cost read-only; the mode menu (one key per step); the model pill opens the agent's picker in the drawer (pi: a real menu).

Next, in this order: the pi bridge (one file, attaches to running TUIs, can ship with pi-hkandala); opencode's server when the pane has one (SSE is plain lines); then a New Agent launch path that starts Claude Code with Oriel's --settings and Codex with --remote to an app-server in a hidden pane. Left out: restarting agents in structured modes, pi --mode rpc, ACP (they end or fork the TUI's session).

Mock-ups

Five designs for the same view, drawn in HTML and CSS to look like SwiftUI on macOS 26 with Liquid Glass, in Oriel's look (Style.swift: 10 pt cards, the 36 pt card header, the status colors, SF Pro and SF Mono). Each shows the same pieces: collapsed tool groups, a running tool, a permission request, a subagent, a plan or todo list, the model and mode controls, the composer and the chat|term switch. Each uses a different agent to show that one view fits all four. Click a summary line to open or close its group. The switch at the top of the page sets dark or light for all of them. Everything here is plain SwiftUI: ScrollView + LazyVStack, DisclosureGroup, Picker(.segmented), Menu, .glassEffect(), TextField(axis: .vertical), AttributedString(markdown:).

Which design

A in pane cards, C when a card is zoomed or floated, E for the pill card, D's drawer as the fallback inside all of them. A is the densest and matches the pi-content-layout look the user reads all day. Take two things from B: the approval card pins above the composer while it is scrolled out of view, and the plan shows as a small capsule over the composer ("Plan 2 of 4") that opens the list. B's inspector costs too much width in split cards; keep it for later if users ask.

Risks and open questions

Risks

  1. Format churn. Codex replaced its event names within ten releases; Claude Code adds entry types often; opencode 2.x changes storage and API. Parsers must skip what they do not know and key on the version in the file's header.
  2. Typing into a picker. herdr reports idle for pickers and pi's dialogs. The send guard reads the screen; an upstream fix in herdr is better (below).
  3. Side channels need the launch. Claude Code, Codex and opencode 1.x get their side channel only when Oriel starts them. Panes the user started stay on Base.
  4. Writes to the user's config. /model x and Return in pickers (Claude Code, Codex), Esc on Codex's startup promo, pi's /reload (trust.json) all wrote global files during the spikes. The adapters must use the session-only paths.
  5. Policy and races on approvals (above): show what really happened, not what was clicked.

Open questions for the user

  1. Should Oriel start agents? A New Agent menu that launches Claude Code with Oriel's --settings, Codex with --remote and an app-server pane, and opencode with --port is the only way to give those three live text and in-chat approvals. It changes how agents start (and bypasses the user's shell aliases).
  2. The pi bridge: ship it in pi-hkandala (loaded everywhere pi-hkandala is installed, so remote machines get it too), or have Oriel copy it to each machine? The second breaks "nothing installed on machines".
  3. Codex remote: a line↔WebSocket shim sent with each run (Perl is on every machine the relay works on), or Codex side channel on This Mac only?
  4. History: keep the 256 KiB start, or page back further on scroll?
  5. Upstream asks for herdr: keep Claude Code's transcript_path; follow /branch and Codex /fork; report blocked for pickers and pi's ui_prompt dialogs; detect opencode 2.x.
